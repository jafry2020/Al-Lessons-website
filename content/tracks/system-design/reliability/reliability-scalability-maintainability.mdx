    shortAnswer: "A fault is a component deviating from spec — a disk corrupting a sector, a developer pushing a bad config. A failure is the whole system no longer providing its service. Fault tolerance means faults don't become failures."
    detailed: |
      Kleppmann is precise about this. A fault is local — one component misbehaving. A failure is global — users notice. A reliable system contains faults so they don't propagate into failures.

      That framing changes what you build. You can't prevent every fault; you can engineer the system so faults are absorbed (replication, retries, idempotency) before they reach the user. Netflix's Chaos Monkey deliberately injects faults so the team is forced to design containment paths.

  - question: "Twitter's fan-out problem: what changed when they scaled?"
    shortAnswer: "At small scale, computing each user's home timeline on read (joining tweets + follows) was cheap. At large scale, reads dominated writes by ~100×, so they precomputed timelines on write — until celebrities made write fan-out explode."
    detailed: |
      The naive approach (fan-out on read): when a user opens their feed, query 'all tweets by people I follow, ordered by time, limit 100'. Cheap to write a tweet (1 insert), expensive to read a feed (a big join).

      The optimization (fan-out on write): when someone tweets, push that tweet into a precomputed feed for every follower. Now reads are cheap (one lookup), writes are expensive (write-amplification proportional to follower count).

      This is the book's canonical example of describing load with the right parameter. 'Tweets per second' is the wrong number; 'follower fan-out distribution' is closer to what determines architecture.
    pitfalls:
      - "Don't pick fan-out on read or write as universally correct — the answer depends on read:write ratio and fan-out distribution."

<TldrCallout>
  Every data-intensive application is graded on three properties: *reliability* (does it keep
  working when things go wrong?), *scalability* (does it keep working as load grows?), and
  *maintainability* (can the team keep changing it without breaking it?). Each one has specific
  failure modes and specific design moves. The next seven modules are essentially detailed playbooks
  for the three.
</TldrCallout>

## What "data-intensive" means

<GlossaryTerm
  term="Data-intensive application"
  definition="A system whose main challenges come from the amount, complexity, or rate of change of its data — not from raw CPU. Most modern applications are data-intensive: storing user data, replicating it, querying it, keeping it correct as it changes."
>
  Data-intensive applications
</GlossaryTerm>
are systems whose hardest problems are about *data* — storing it, fetching it, replicating it,
keeping it correct under concurrent change. They're contrasted with *compute-intensive* systems
(numerical simulations, video encoding) where CPU is the bottleneck. Almost every application you'll
build in the 2020s is data-intensive.

The implication: building one well doesn't mean writing tight loops. It means picking the right database, encoding, and replication strategy — and accepting that the hardest problems will surface at the boundaries between systems.

## The three pillars

### Reliability

<GlossaryTerm
  term="Reliability"
  definition="The system continues to provide its service correctly, even when things go wrong. Not the same as availability — a reliable system tolerates faults so they don't become user-visible failures."
>
  Reliability
</GlossaryTerm>
is about surviving things going wrong. Kleppmann is precise about the vocabulary: a *fault* is a
component deviating from spec; a *failure* is the system no longer providing its service. The goal
isn't zero faults — those are inevitable. The goal is no failures.

There are three flavors of fault the book asks you to budget for:

- **Hardware faults.** Disks die. Memory corrupts. Power supplies fail. At small scale they're rare. At fleet scale you lose multiple components a day. The standard response is redundancy (replicated storage, multiple availability zones).
- **Software errors.** A leap-second triggers a kernel bug. A memory leak slowly fills RAM. A runaway query monopolizes the database. These are nastier than hardware faults because they're _correlated_ — one trigger takes down many machines at once.
- **Human errors.** A developer pushes the wrong config. A DBA runs a migration during business hours. The book is blunt: humans are the leading source of outages. Design systems where the easy path is the safe path.

### Scalability

<GlossaryTerm
  term="Scalability"
  definition="The ability of a system to cope with increased load. 'Scalable' is meaningless without naming the load parameter — is the system scaling to handle more users, more data, more requests per second, longer connections? Different parameters drive different architectures."
>
  Scalability
</GlossaryTerm>
is not a property a system has — it's a question you ask: *as some specific load parameter grows,
how does the system's performance change?* "Scalable" without a load parameter is marketing.

The book's classic load-description example is Twitter. Two operations dominate: posting a tweet (~5k writes/sec average, ~12k peak) and viewing the home timeline (~300k reads/sec). The right parameter to describe load isn't just throughput — it's the _fan-out distribution_: how many followers does each user have? That number drives the architectural choice.

<WorkedExample title="Twitter's fan-out tradeoff">

**The problem.** When a user opens their home timeline, they should see the most recent tweets from everyone they follow.

**The naive approach (fan-out on read).** Store tweets in one table. When a user requests their feed, join tweets against follows: `SELECT * FROM tweets WHERE author IN (SELECT followee FROM follows WHERE follower = me) ORDER BY time DESC LIMIT 100`. Tweets are cheap to write. Feeds are expensive to read.

**Why it breaks.** Reads happen 100× more than writes. Every feed load triggers a giant join. The database cracks under read load.

**The real solution (fan-out on write).** When you tweet, push the tweet into a precomputed timeline for each of your followers. Now reads are a single lookup. Writes are expensive — write-amplification proportional to follower count.

**The tradeoff.** Fan-out on write trades write cost for read cost, which is correct on average. But Justin Bieber has 30 million followers. Every tweet becomes 30 million writes, often clustered in seconds. Twitter ended up _hybrid_ — fan-out on write for normal users, fan-out on read for celebrities, merged at the timeline assembly step.

</WorkedExample>

### Maintainability

<GlossaryTerm
  term="Maintainability"
  definition="The ability of the team to keep the system running, understandable, and modifiable as it ages. Made up of operability (running it), simplicity (understanding it), and evolvability (changing it)."
>
  Maintainability
</GlossaryTerm>
is the property that's hardest to feel until it's gone. The book splits it into three sub-goals:
*operability* (the ops team can do their job — good monitoring, clear runbooks, predictable
behavior), *simplicity* (you fight accidental complexity), and *evolvability* (you can change the
system without rewriting it).

Most legacy-rewrite projects are evolvability failures, not performance failures. The original team made local choices that, compounded, made the system rigid. The job of architecture is to keep changes cheap years later.

## Percentiles: why averages lie

<GlossaryTerm
  term="Percentile (p99)"
  definition="The value below which a given fraction of measurements fall. p99 latency = 99% of requests are faster than this; 1% are slower. p99.9 is the same with three nines. Percentiles describe tail behavior, which averages hide."
>
  Percentiles
</GlossaryTerm>
are the only honest way to talk about latency. Consider 1000 requests where 990 take 5ms and 10 take
4000ms. The *average* latency is 45ms — a number no user experienced. The p50 (median) is 5ms
(fast). The p99 is somewhere in the slow tail (broken-feeling). Different users live in different
parts of the distribution.

The book repeats Amazon's finding: improvements to p99.9 latency moved revenue measurably. p99.9 is the tail every customer eventually hits — even fast users get unlucky once in a thousand requests, and the slow requests are disproportionately important users (more data, more cart history, more joins). Always quote tail percentiles.

<AnalogyCallout>
  Latency is like rainfall. Saying "it rained an average of 4mm this month" is useless if all 120mm
  fell in three hours one afternoon. The flood damage doesn't care about the average — it cares
  about the peak.
</AnalogyCallout>

## What this means in practice

When you read a postmortem, ask: which pillar failed? When you pick a database, ask: which load parameter dominates? When you set up monitoring, never plot the average — always plot p50, p95, and p99 together.

The rest of this course is a tour through specific techniques the book uses to defend the three pillars: data models, storage engines, encoding, replication, partitioning, transactions, and distributed-systems primitives. Each one is a tool for buying back reliability, scalability, or maintainability at a different layer of the stack.
