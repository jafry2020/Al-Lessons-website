  - question: "What's a word embedding?"
    shortAnswer: |
      A dense vector representation of a word in some learned space, where geometric properties (distance, direction) reflect semantic properties. Word2Vec (Mikolov 2013) was the breakthrough; modern systems use contextual embeddings instead.
    detailed: |
      Word2Vec trained a small neural network to predict surrounding words from a target word (or vice versa). The byproduct: a 100-300 dim vector for each word in the vocabulary, where similar words have nearby vectors.

      Famous example: vec("king") - vec("man") + vec("woman") ≈ vec("queen"). The arithmetic suggests learned semantic dimensions like "gender" and "royalty" emerge from the data.

      Properties:
      - Static: each word has one vector. "Bank" the financial institution and "bank" the riverbank get the same vector.
      - Trained on a fixed vocabulary; out-of-vocab words have no embedding.
      - Cheap to compute, cheap to use.

      GloVe (Pennington, Socher, Manning, 2014) is a similar method using global co-occurrence counts. Same idea, slightly different math, similar results.

      Word2Vec / GloVe ruled NLP from 2013 to 2018. Then contextual embeddings (ELMo, BERT) replaced them, because they handle polysemy and context.
    pitfalls:
      - "Word2Vec embeddings learned biases from training data ('doctor' near 'man', 'nurse' near 'woman'). Modern systems still inherit such biases unless explicitly mitigated."
  - question: "What's a contextual embedding?"
    shortAnswer: |
      A vector for each token that depends on the surrounding text. BERT (Devlin et al., 2018) produces a different vector for "bank" in "river bank" vs. "savings bank". Contextual embeddings dominate modern NLP.
    detailed: |
      A transformer encoder (BERT-style) reads the entire sequence and produces one vector per input token. Each vector encodes both the token identity AND its role in the surrounding context.

      Example: in "I deposited money at the bank", the vector for "bank" encodes "financial institution." In "I sat by the river bank", the same token gets a different vector — closer to "shore" than to "savings."

      Why this matters: polysemous words have one vector with static embeddings (averaging the senses); contextual embeddings disambiguate per usage.

      Uses:
      - Input features for downstream models (fine-tuning).
      - Token-level tasks (NER, POS tagging, span extraction).
      - Sentence-level tasks via pooling (with caveats — see next).

      Modern frontier models (GPT-4, Llama) also produce contextual embeddings (the hidden states of any layer), but accessing them requires running the full model.
    pitfalls:
      - "Contextual embeddings from different layers have different properties: low layers capture syntax, high layers capture semantics. Layer choice matters for some tasks."
  - question: "Why do we need sentence-transformers instead of just BERT [CLS]?"
    shortAnswer: |
      BERT's [CLS] token is trained for classification, not similarity. Cosine similarity between [CLS] vectors is unreliable. Sentence-transformers (Reimers & Gurevych, 2019) explicitly trains the model so that cosine similarity matches semantic similarity.
    detailed: |
      Vanilla BERT outputs one vector per input token. To get a sentence vector, the obvious approaches are:

      - **[CLS] token**: BERT's first token, intended for classification. Cosine similarity between [CLS] vectors poorly correlates with semantic similarity.
      - **Mean pooling**: average token vectors. Slightly better than [CLS] but still not great.

      Reimers & Gurevych (2019) fine-tuned BERT with a siamese architecture (two BERT encoders sharing weights) and a contrastive loss, so that similar sentences end up close in vector space and dissimilar sentences far apart. The result: sentence-BERT (SBERT), the basis of the modern sentence-transformers library.

      Modern sentence-transformer models (BGE, E5, GTE, Cohere embed-v3, OpenAI embedding-3) are all trained with similar contrastive objectives. The differences are in scale, training data, and dimensionality.
    pitfalls:
      - "If you need sentence embeddings, never use raw BERT [CLS]. Always use a model trained for the task (sentence-transformers, BGE, E5, OpenAI embeddings)."

  - question: "Can I mix embeddings from different models?"
    shortAnswer: |
      No. Each model has its own learned embedding space; cosine similarity between vectors from different models is meaningless. Re-embed your entire corpus when you switch models.
    detailed: |
      Two embedding spaces from different models (even from the same family with different sizes) are not aligned. A vector from BGE-large and a vector from OpenAI text-embedding-3 occupy different geometric spaces; their cosine similarity is essentially random.

      Implications:
      - If you upgrade your embedding model, you must re-embed your entire corpus and rebuild your index.
      - You cannot search a corpus embedded with model A using a query embedded with model B.
      - "Embedding alignment" research exists but isn't production-ready for most cases.

      Operational reality: pick an embedding model carefully because changing it is expensive. For very large corpora (>10M docs), re-embedding can take days.
    pitfalls:

  - question: "What about LLM-as-embedder?"
    shortAnswer: |

      - Useful for tasks requiring deep reasoning embedded in the representation.

      - 10-100× slower to compute than dedicated embedding models.

      - On standard retrieval benchmarks, doesn't dramatically beat specialised models trained on retrieval data.

## The progression

Three generations of text embeddings:

| Generation                                | Examples                                                | Properties                                   |
| ----------------------------------------- | ------------------------------------------------------- | -------------------------------------------- |
| **Static word embeddings** (2013-2018)    | Word2Vec, GloVe, fastText                               | One vector per word; ignores context         |
| **Contextual embeddings** (2018-)         | BERT, RoBERTa, GPT hidden states                        | One vector per token; depends on context     |
| **Sentence / passage embeddings** (2019-) | sentence-transformers, BGE, E5, OpenAI text-embedding-3 | One vector per chunk; trained for similarity |

Each generation solved a limitation of the previous. By 2026, sentence / passage embeddings dominate production retrieval and similarity tasks.

## Word2Vec: the breakthrough

Mikolov et al. (2013) trained a small two-layer network to predict surrounding words from a target word ("skip-gram") or vice versa ("CBOW"). The hidden layer's weights become the embeddings.

Famous property: vector arithmetic captures semantic relationships.

vec("king") - vec("man") + vec("woman") ≈ vec("queen")

The embeddings encode dimensions like "gender" and "royalty" implicitly. The model didn't know these existed; they emerged from the data.

Limitations:

- **One vector per word.** "Bank" is ambiguous; one vector averages the senses.
- **Fixed vocabulary.** Out-of-vocabulary words have no embedding (fastText fixed this with subword embeddings).
- **No context awareness.** "The bank approved my loan" and "I sat by the river bank" produce the same "bank" vector.

Word2Vec / GloVe ruled NLP from 2013 to 2018. They were the input features for nearly every NLP task in that period.

## Contextual embeddings: BERT

BERT (Devlin et al., 2018) introduced contextual embeddings: a transformer encoder reads the whole sequence and outputs one vector per input token, where each vector depends on the surrounding context.

"The bank approved my loan" → vector for "bank" near "credit", "money", "finance"
"I sat by the river bank" → vector for "bank" near "shore", "water", "stream"

Same token; different vector. Polysemy resolved.

How to get a sentence vector from BERT (the next problem):

- **[CLS] token**: BERT's first input token, intended as a classification target. Cosine similarity between [CLS] vectors poorly tracks semantic similarity.
- **Mean pooling**: average all token vectors. Slightly better than [CLS] but not great.

Both approaches are mediocre because BERT was trained for masked language modelling, not for similarity. The fix: train explicitly for similarity.

## Sentence-transformers: trained for similarity

Reimers & Gurevych (2019) modified BERT for sentence similarity:

1. Two BERT encoders share weights (siamese architecture).
2. Pass two sentences through them; get two vectors.
3. Train with a contrastive loss: similar pairs should have high cosine similarity, dissimilar pairs low.

The result is **sentence-BERT** (SBERT), and more generally the modern sentence-transformer family. Their key property: **cosine similarity between vectors reliably tracks semantic similarity**.

In 2026, all production retrieval / similarity systems use models trained this way. Examples:

| Model                   | Provider         | Dim                     | Multi-lingual?  |
| ----------------------- | ---------------- | ----------------------- | --------------- |
| BGE-large-en            | open / BAAI      | 1024                    | English-focused |
| BGE-M3                  | open / BAAI      | 1024                    | 100+ languages  |
| E5-large-v2             | open / Microsoft | 1024                    | English         |
| multilingual-e5-large   | open / Microsoft | 1024                    | 100+ languages  |
| nomic-embed-text        | open / Nomic     | 768                     | English         |
| text-embedding-3-large  | OpenAI API       | up to 3072 (Matryoshka) | Multi           |
| embed-multilingual-v3.0 | Cohere API       | 1024                    | 100+ languages  |
| voyage-3                | Voyage AI API    | 1024                    | Multi           |

Pick one based on quality, dim (storage), latency, and cost. Don't mix.

## What you do with embeddings

Five common production uses:

1. **Retrieval (RAG, semantic search)**. Embed documents, store in vector DB. At query time, embed query, find nearest documents. See A6.6.

2. **Classification (feature extraction)**. Embed text, train a small classifier on top. Faster than fine-tuning a full transformer for tasks with many labels but limited training data.

3. **Clustering**. Embed corpus, run UMAP + HDBSCAN. Discover topics, near-duplicates, customer themes.

4. **Recommendation**. Embed items and users; recommend nearest items per user. Often combined with collaborative filtering.

5. **Deduplication**. Embed records; flag near-duplicates by cosine similarity threshold.

For all of these, the workflow is: pick an embedding model → embed your data once → use the vectors many times.

## Choosing dim and quality

Embedding models offer various output dimensions:

- 384 dim: lightweight (MiniLM); fast, slightly worse quality.
- 768 dim: standard (BERT-base); good baseline.
- 1024 dim: high-quality (BGE-large, E5-large); the production sweet spot in 2026.
- 1536-3072 dim: frontier (OpenAI text-embedding-3-large, some research models); marginal quality gain at storage cost.

A Matryoshka-trained model (OpenAI text-embedding-3, some open models) lets you truncate the vector to lower dim without retraining; useful for storage / quality trade-offs.

Rule of thumb: 1024 dim is usually enough. Going higher costs storage and inference latency for small quality gains.

## Cost engineering for embeddings

For a 10M-document corpus:

- Storage: 10M × 1024 dim × 4 bytes (FP32) = 40 GB. Switch to FP16: 20 GB. Quantise to int8: 10 GB.
- Indexing cost: depends on index type (HNSW, IVF-PQ).
- Compute: embedding 10M docs at ~1k tokens each is ~10B tokens. OpenAI cost: $1300. BGE on a single GPU: a few hours of compute, no API cost.

For most teams, **self-hosting an embedding model** is cheaper than API for >100k documents. APIs are convenient for prototyping and small corpora.

## What embedding models can't do well

- **Long documents**. Most embedding models accept 512 tokens; some go to 8k. For longer documents, chunk and embed each chunk.
- **Code semantics**. Specialised code embeddings (UnixCoder, CodeBERT, codesearchnet-trained) outperform general-purpose models on code retrieval.
- **Out-of-distribution domains**. Medical, legal, scientific text benefit from domain-specific fine-tuning.
- **Multi-modal**. Joint image-text embeddings (CLIP) are a different family with their own properties.

## A note on instructional embeddings

Some modern embedding models (E5, BGE, NV-Embed) are **instruction-tuned**: you prepend a prompt like "Represent this sentence for retrieval:" before embedding. The same model produces different embeddings for the same text depending on the instruction, optimised for different downstream tasks (retrieval vs. classification vs. STS).

In practice: read the model's documentation for the recommended prompt. Skipping it can cost 5-10 points on retrieval benchmarks.

## Closing for embeddings

Modern embeddings are the workhorse of production NLP. They power retrieval (RAG), similarity (deduplication, recommendation), and clustering (topic modelling, customer segmentation). In 2026 the question is rarely "should I use embeddings?" but "which one?" — and the answer is usually BGE-large, E5-large, or one of the major API embedding products.
