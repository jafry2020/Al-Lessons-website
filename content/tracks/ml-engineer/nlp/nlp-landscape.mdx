  - question: "When should you use an LLM API vs. a fine-tuned small model?"
    shortAnswer: |
      LLM API when: low volume, varied tasks, fast iteration, quality matters. Fine-tuned small model when: high volume, fixed task, latency / cost-sensitive, data sensitivity (on-prem).
    detailed: |
      Decision factors:

      - **Volume.** At 1k requests/day, LLM APIs are cheap. At 10M requests/day, even a $0.50/M-token API costs $5k/day — a fine-tuned 100M encoder running on 1 GPU is much cheaper.

      - **Latency.** Frontier LLMs add 500ms-2s of latency. A DistilBERT-style classifier runs in 10ms. For real-time UX, the small model wins.

      - **Task variability.** If the task changes daily (different categories, formats, asks), prompting an LLM is faster than retraining. If the task is fixed (sentiment of customer reviews), a fine-tuned model is more efficient.

      - **Data sensitivity.** Some industries (healthcare, finance) can't send data to third-party APIs. Self-hosted models are the only option.

      - **Quality ceiling.** Frontier LLMs are smarter at reasoning tasks. A small fine-tuned model can match on narrow tasks but not on open-ended reasoning.

      Common pattern in 2026: prototype with LLM API, validate the task, then distill to a small fine-tuned model if volume / cost justifies it.
    pitfalls:
      - "'Distillation' means using LLM outputs as training data for a smaller model. Standard pattern; legal terms matter (OpenAI prohibits this for some uses; check)."
  - question: "What NLP tasks are nearly solved in 2026?"
    shortAnswer: |
      Text classification, sentiment analysis, named entity recognition, language detection, translation, summarisation, basic question answering. All have strong pretrained baselines that work out of the box for most use cases.
    detailed: |
      "Nearly solved" doesn't mean perfect — it means a strong pretrained baseline exists and most production work is fine-tuning or prompting on top.

      | Task | 2026 default |
      | ---- | ------------ |
      | Sentiment | Fine-tune RoBERTa / ModernBERT |
      | Topic classification | Fine-tune small encoder or prompt LLM |
      | NER (general entities) | spaCy or fine-tuned encoder |
      | Translation | NLLB / Llama / dedicated MT model |
      | Summarisation | Prompt LLM |
      | Language detection | fastText (a 2017 library, still SOTA for its task!) |
      | Sentence similarity | sentence-transformers |
      | Tokenisation | tiktoken / SentencePiece |

      What's NOT nearly solved:
      - Multi-hop reasoning over long documents.
      - Hallucination-free generation.
      - Truly robust handling of out-of-distribution input.
      - Low-resource languages (anything except top ~50 languages).
      - Domain-specific NLP requiring deep expertise (medical, legal, scientific).
    pitfalls:
      - "'Nearly solved' is dangerous. Production systems still need careful evaluation, monitoring, and fallbacks."
  - question: "Where does classical NLP (spaCy, NLTK, regex) still fit?"
    shortAnswer: |
      Anywhere deterministic behaviour, fast inference, no GPU dependency, or interpretable rules are required. Tokenisation, sentence segmentation, POS tagging, simple NER, rule-based parsing.
    detailed: |
      Classical NLP libraries are not obsolete. They're complementary to neural NLP:

      - **spaCy**: pipeline for tokenisation, sentence segmentation, POS, NER, dependency parsing. Fast (millions of tokens / minute), CPU-only, deterministic. Still the workhorse for preprocessing.
      - **NLTK**: educational library; some unique data resources (corpora, lexicons).
      - **regex / text manipulation**: extracting dates, phone numbers, structured patterns from text. Often faster and more reliable than LLM extraction.
      - **fastText**: word embeddings + classification + language detection. Pre-deep-learning era but Facebook still maintains it; remains the SOTA for language detection.

      Pattern: use classical tools for the deterministic / structured parts; reach for neural models when the task involves semantic understanding.
    pitfalls:
      - "Don't 'ask GPT' for tasks where a regex would work. Cheaper, more reliable, more interpretable."
  - question: "What's the 2026 'starter stack' for a new NLP project?"
    shortAnswer: |
      HuggingFace Transformers for models, tokenizers, datasets. spaCy for preprocessing if needed. OpenAI / Anthropic API for prompting. sentence-transformers for embeddings. pgvector or Faiss for retrieval. Weights & Biases or MLflow for experiment tracking.
    detailed: |
      The convergent 2026 starter stack:

      - **HuggingFace Transformers**: load any pretrained model with `from_pretrained()`. The default for inference and fine-tuning of open-weights models.
      - **HuggingFace Datasets**: standard format for training data, with caching and streaming.
      - **HuggingFace tokenizers**: fast, Rust-backed tokenizers for BPE / WordPiece / SentencePiece.
      - **sentence-transformers**: embedding models for retrieval, similarity, clustering.
      - **OpenAI / Anthropic Python SDKs**: prompting and structured output from frontier APIs.
      - **LangChain / LlamaIndex** (optional): higher-level RAG / agent frameworks. Useful for prototyping; production systems often roll their own.
      - **pgvector** (Postgres) or **Faiss**: vector indexes.
      - **vLLM** or **TGI**: high-throughput LLM serving for self-hosted models.
      - **Weights & Biases**: experiment tracking and evaluation dashboards.

      Most production NLP work uses 4-6 of these.
    pitfalls:
      - "Don't conflate 'use LangChain' with 'build a real system.' LangChain is a prototyping library; production usually replaces large parts of it."

  Claude, Gemini) for fast iteration and reasoning-heavy work. Fine-tuned small encoders

## The LLM-vs-fine-tune decision

For a given NLP task, the high-level decision in 2026:

```
              quality
                ^
                |
   fine-tuned   |
   small model  |       LLM API
       o--------|------------o
                |
                |
                +--------------> cost / latency
              low                       high
```

The fine-tuned small model is to the bottom-left (low cost, fast); the LLM API is to the upper-right (higher quality, slower, more expensive per request). For most tasks the curve is roughly:

- **< 1k requests/day**: LLM API. The development cost saved dominates.
- **1k - 100k/day**: depends. If task is fixed and well-defined, fine-tuned model. Otherwise LLM.
- **> 100k/day**: fine-tuned small model. Even at $0.50/M tokens, 1M requests/day at 500 tokens each is $250/day = $7.5k/month — a fine-tuned DistilBERT on one GPU is cheaper.

Add data-sensitivity, latency, and team capacity as further inputs.

  problems. Employee: more expensive up front, cheaper per task, handles repetitive work well. Most
  companies have both; the question is for which work.

## What pretrained foundation models eat

By 2026, large pretrained foundation models have absorbed:

- **Most "classical NLP" tasks** at near-or-better quality with no task-specific training (just prompting).
- **Hand-engineered feature pipelines** for text (TF-IDF, n-grams, etc. — only used in low-resource baselines now).
- **Specialised seq2seq models** (translation, summarisation) — LLM API often comparable to dedicated MT systems.
- **Rule-based parsers** for ambiguous tasks — still beaten by rules for deterministic / structured extraction.

What they haven't (yet) eaten:

- **Truly low-latency NLP** — LLMs add hundreds of ms; fine-tuned encoders run in ms.
- **Deterministic structured extraction** — regex / spaCy more reliable for date / phone / address / SKU extraction.
- **Domain-specific models** — PubMedBERT outperforms GPT-3 on some medical NLP at much lower cost.
- **Sentence embeddings for retrieval** — specialised models (BGE, E5, sentence-transformers) beat general LLM embeddings.
- **Hardcore preprocessing** — fast tokenization, sentence splitting, normalisation.

## A reasonable mental model

Think of the 2026 NLP stack in three layers:

1. **Preprocessing layer** (deterministic, fast): tokenisation, sentence segmentation, normalisation, regex extraction. Tools: spaCy, tiktoken, regex.

2. **Representation layer** (learned, batched): convert text into vectors for retrieval, classification, similarity. Tools: sentence-transformers, fine-tuned encoders.

3. **Reasoning layer** (LLM, on-demand): open-ended generation, multi-step reasoning, instruction following. Tools: GPT-4, Claude, Llama-served-with-vLLM.

Different tasks live at different layers. Many real systems combine all three: preprocess input, embed for retrieval, hand top-k results to LLM for generation. (That's the RAG pattern — A6.6.)

## The two paradigm shifts worth knowing

**Shift 1: Foundation models replaced from-scratch training.**
Before 2018, an NLP project meant designing features and training a model on your data. After 2018 (BERT) and especially after 2020 (GPT-3), every project starts from a pretrained model. Training NLP models from scratch is almost exclusively a research activity.

**Shift 2: LLM APIs replaced most "deploy a custom model" projects.**
For tasks where ~$0.001 per request is fine, you can prompt GPT-4 or Claude and skip the entire MLOps stack. The "build, train, deploy a custom model" workflow only makes sense above a volume / sensitivity / latency threshold.

These shifts have created a different kind of NLP engineer: less custom modelling, more prompt engineering, more retrieval, more evaluation infrastructure.
