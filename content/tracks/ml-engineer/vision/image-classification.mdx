      Pretrained backbone (ConvNeXt-Base or ViT-B from timm / HuggingFace) → replace final classifier head → fine-tune with AdamW, cosine schedule, low lr (1e-4 or 1e-5), 5-30 epochs, strong augmentation, mixed precision.

      The 2026 recipe (timm-flavoured):

      ```python
      import timm
      import torch
      from torch.optim import AdamW
      from torch.optim.lr_scheduler import CosineAnnealingLR

      model = timm.create_model(
          "convnext_base.fb_in22k_ft_in1k",  # ImageNet-22k + 1k fine-tuned
          pretrained=True,
          num_classes=NUM_CLASSES,  # replace head
      )
      model.cuda()

      optimizer = AdamW(model.parameters(), lr=1e-4, weight_decay=0.05)
      scheduler = CosineAnnealingLR(optimizer, T_max=NUM_EPOCHS)
      scaler = torch.cuda.amp.GradScaler()

      for epoch in range(NUM_EPOCHS):
          for x, y in train_loader:
              x, y = x.cuda(), y.cuda()
              optimizer.zero_grad()
              with torch.cuda.amp.autocast(dtype=torch.bfloat16):
                  logits = model(x)
                  loss = soft_cross_entropy(logits, y)  # for mixed labels
              scaler.scale(loss).backward()
              scaler.step(optimizer)
              scaler.update()
          scheduler.step()
      ```

      Key parameters:
      - `lr=1e-4` for full fine-tune; `lr=1e-3` for linear probe.
      - `weight_decay=0.05` for transformer-style; `0.01` for CNNs.
      - 5-30 epochs (more for tiny data; fewer for huge data).
      - BF16 mixed precision on modern GPUs.

      For HuggingFace: same idea but `AutoModelForImageClassification.from_pretrained(...)` + `Trainer`.
    pitfalls:
      - "Don't use the pretraining learning rate. Fine-tuning needs 10-100× smaller lr to avoid catastrophic forgetting."

  - question: "When should you fine-tune vs. zero-shot CLIP vs. LLM?"
    shortAnswer: |
      Fine-tune when: >500 labelled examples, fixed classes, high-volume inference, latency-sensitive. CLIP zero-shot when: very few or no labels, broad classes. LLM (GPT-4V) when: novel reasoning / explanation, very low volume.
    detailed: |
      | Situation | Approach |
      | --------- | -------- |
      | < 100 labelled examples per class | CLIP zero-shot or LLM prompting |
      | 100-1k per class | Linear probe on frozen DINOv2 / CLIP features |
      | 1k-10k per class | Fine-tune small backbone (ConvNeXt-Tiny, ViT-S) |
      | 10k+ per class | Fine-tune medium backbone (ConvNeXt-Base, ViT-B) |
      | Novel categories evolving weekly | CLIP zero-shot (no retraining) |
      | Need explanation alongside class | LLM (GPT-4V, Claude vision) |
      | Real-time, > 100 req/sec | Fine-tuned small backbone |
      | Image search / open-vocab | CLIP retrieval (not classification) |

      CLIP zero-shot accuracy: ~75% on ImageNet (vs. 85% for a fine-tuned model). The gap is narrower for visually distinct classes; wider for fine-grained.

      LLM (GPT-4V) zero-shot is competitive on broad tasks (~80% on coarse classification benchmarks) but very expensive at scale.
    pitfalls:
      - "Zero-shot CLIP is brittle to label phrasing. 'a photo of a {class}' templates matter; sometimes engineered templates lift accuracy 5%."
  - question: "How do you handle long-tail / class imbalance for vision?"
    shortAnswer: |
      Class-balanced sampling, weighted loss, focal loss for severe imbalance, or two-stage training (pretrain on all, fine-tune on balanced subset). Modern alternative: distill from a CLIP zero-shot baseline trained on the long-tail.
    detailed: |
      Long-tail (rare classes) is endemic in real CV data. Approaches:

      **Class-balanced sampling.** Each class sampled with equal probability per epoch (not by frequency). Easy fix; sometimes overfits rare classes.

      **Weighted loss.** `CrossEntropyLoss(weight=1/freq)`. Less aggressive than rebalancing samples.

      **Focal loss** (Lin et al., 2017). Down-weights easy / well-classified examples; focuses on hard ones. Originally for object detection; useful for severe imbalance in classification.

      **Two-stage**: Stage 1 train on full imbalanced data; stage 2 fine-tune classifier head on class-balanced data. Often best of both worlds.

      **CLIP distillation**: get CLIP zero-shot predictions for all classes (works for any class by name), use as soft labels for fine-tuning. Helps with rare classes since CLIP saw them in pretraining.

      **LDAM, BSCE losses**: research-grade losses specifically for long-tail. Worth knowing exists; rarely worth implementing custom.

      Practical: stratified split + class-balanced sampling + focal loss handles 80% of imbalanced cases.
    pitfalls:
      - "Aggressive rebalancing breaks calibration. The model thinks rare classes are common in deployment; predictions over-confident."
  - question: "How do you evaluate beyond top-1 accuracy?"
    shortAnswer: |
      Per-class accuracy / F1, confusion matrix, calibration plot, performance on important slices (camera, location, demographics), failure mode analysis on 50-100 hand-inspected mistakes. Top-1 hides many production failures.
    detailed: |
      A production-ready evaluation goes beyond top-1:

      **Per-class F1 + confusion matrix.** Reveals which classes confuse the model. Often 80% of errors are between 2-3 confusable classes.

      **Slice metrics.** Compute accuracy on subsets: by camera, by lighting condition, by time-of-day, by image source. Look for big gaps. Production failures often hide in slices.

      **Calibration.** Reliability plots show whether predicted probabilities match actual accuracy. Many fine-tuned models are over-confident; calibration matters when downstream code uses probabilities.

      **Robustness suite.** ImageNet-C (corruptions), ImageNet-V2, custom adversarial / OOD data. Track over time.

      **Manual error inspection.** Look at 50-100 misclassified examples by hand. You'll find systematic errors (labelling bugs, augmentation artefacts, distribution gaps) that metrics miss.

      Tools: Weights & Biases for tracking, custom dashboards for slices, FiftyOne for image-level dataset inspection.
    pitfalls:
      - "Don't compare top-1 accuracy across models with different evaluation sets / augmentation. Standardise the eval before comparing."
  - question: "What's the LoRA story for vision?"
    shortAnswer: |
      LoRA for vision exists and works: parameter-efficient fine-tuning by adding low-rank adapters to attention or convolution layers. Less critical than for LLMs because vision backbones are smaller (10-300M params vs. billions); often easier to just full-fine-tune.
    detailed: |
      LoRA (low-rank adaptation) adds small trainable matrices to frozen pretrained weights. For ViTs, applied to attention Q/K/V projections (like LLM LoRA).

      When useful in vision:
      - Very large backbones (DINOv2-L, EVA-02-L, ViT-H — 300M+ params).
      - Adapting CLIP or SigLIP without losing zero-shot capabilities.
      - Multi-task adaptation (one base model + many LoRA adapters per task).

      When unnecessary:
      - Small backbones (ConvNeXt-Tiny, ViT-B) — full fine-tune is cheap.
      - Single-task deployments.
      - When backbone quality matters more than parameter efficiency.

      Libraries: HuggingFace PEFT supports vision LoRA; timm has hooks for custom adapters.

      The vision community uses LoRA much less than the LLM community precisely because vision backbones are 10-100× smaller — full fine-tune is feasible.
    pitfalls:
      - "Vision LoRA rank r matters less than LLM LoRA rank. r=8-16 covers most vision use cases."

## The default recipe

20 lines with timm:

```python
import timm
import torch
from torch.optim import AdamW
from torch.optim.lr_scheduler import CosineAnnealingLR

model = timm.create_model(
    "convnext_base.fb_in22k_ft_in1k",
    pretrained=True,
    num_classes=NUM_CLASSES,
)
model.cuda()

optimizer = AdamW(model.parameters(), lr=1e-4, weight_decay=0.05)
scheduler = CosineAnnealingLR(optimizer, T_max=NUM_EPOCHS)
scaler = torch.cuda.amp.GradScaler()

for epoch in range(NUM_EPOCHS):
    for x, y in train_loader:
        x, y = x.cuda(), y.cuda()
        optimizer.zero_grad(set_to_none=True)
        with torch.cuda.amp.autocast(dtype=torch.bfloat16):
            logits = model(x)
            loss = criterion(logits, y)
        scaler.scale(loss).backward()
        scaler.step(optimizer)
        scaler.update()
    scheduler.step()
```

That's a working production-grade fine-tune. Add the augmentation pipeline from A7.2, evaluation, checkpointing — production code is ~200 lines.

## Choosing a backbone

The 2026 default lineup:

| Backbone                           | When                                                                                |
| ---------------------------------- | ----------------------------------------------------------------------------------- |
| **ConvNeXt-Base / Large**          | Safe default; well-supported; quality + reasonable cost                             |
| **ViT-B/16** (timm or HuggingFace) | ViT-flavoured default                                                               |
| **DINOv2-derived ViT-B/L**         | Best self-supervised features; especially good for transfer to non-ImageNet domains |
| **EfficientNetV2**                 | Quality + efficiency balance                                                        |
| **EfficientNet-Lite, MobileNetV3** | Edge / mobile deployment                                                            |
| **SigLIP-ViT**                     | Vision-language adjacent pipelines                                                  |
| **EVA-02, ConvNeXt v2-Huge**       | SOTA general purpose; expensive                                                     |

For most projects: **start with ConvNeXt-Base**. It's a strong baseline with good documentation; failures are easier to diagnose than with newer architectures.

For tasks where pretraining data matters (specialised domains: medical, satellite, microscopy): try DINOv2-derived backbones. The self-supervised pretraining transfers better than ImageNet supervised pretraining for many non-natural-image tasks.

ResNet-50, ResNet-101: now teaching baselines only. Don't pick for new projects; ConvNeXt-Tiny matches them at similar parameter count and much better quality.

## Hyperparameters that matter

| Hyperparameter  | Recommendation                                                                  |
| --------------- | ------------------------------------------------------------------------------- |
| Learning rate   | 1e-4 for full fine-tune, 1e-3 for linear probe; 5e-5 if catastrophic forgetting |
| Weight decay    | 0.05 (transformers / ConvNeXt), 0.01 (CNNs)                                     |
| Optimizer       | AdamW, betas (0.9, 0.999)                                                       |
| Schedule        | Cosine with 5% warmup                                                           |
| Epochs          | 5-30 depending on data size and fine-tuning regime                              |
| Batch size      | 64-256 per GPU (max what fits)                                                  |
| Mixed precision | BF16 (A100/H100); FP16 with GradScaler (older)                                  |
| Resolution      | 224 default; 384 for higher quality at higher cost                              |
| Augmentation    | RandAugment(2, 9) + Mixup(0.2) + CutMix + RandomErasing(0.25)                   |
| Label smoothing | 0.1                                                                             |

These defaults handle 90% of cases. Tune from here.

For very small data (<500 per class), reduce lr (3e-5), reduce epochs (3-5), reduce augmentation magnitude, use linear probe instead of full fine-tune.

<AnalogyCallout>
  Fine-tuning a pretrained backbone is like sharpening a Swiss Army knife for one specific use. The
  metal (the pretrained features) is already good. You just adjust the angle for your task — a few
  degrees, not a complete reshape. Use the same tools (AdamW), gentler force (small lr, few epochs),
  and trust the existing edge.
</AnalogyCallout>

## Linear probe: when full fine-tune is overkill

Linear probe: freeze the backbone; train only a linear classifier on top.

```python
model = timm.create_model("vit_large_patch14_dinov2.lvd142m", pretrained=True, num_classes=0)
for p in model.parameters():
    p.requires_grad = False

# Extract features once
features_train = []
for x in train_loader:
    with torch.no_grad():
        features_train.append(model(x.cuda()))
features_train = torch.cat(features_train)

# Train linear classifier (sklearn LogisticRegression or PyTorch Linear)
from sklearn.linear_model import LogisticRegression
clf = LogisticRegression(max_iter=1000)
clf.fit(features_train.cpu(), labels_train)
```

Pros:

- Fast: train in seconds-to-minutes.
- Robust to small data — won't overfit the way full fine-tune does.
- Reproducible.
- Multi-task: same features feed multiple classifiers.

Cons:

- Slightly lower accuracy than full fine-tune (3-5 points on most benchmarks).
- Limited by pretrained features.

In 2026, **linear probing of DINOv2 backbones is a remarkably strong baseline** — often within 2-3 points of full fine-tuning, at a fraction of the training cost. Default for any "I have <1000 labelled examples per class" task.

## CLIP zero-shot: no training at all

For broad categories or evolving label spaces, CLIP zero-shot classification is competitive:

```python
from transformers import CLIPProcessor, CLIPModel

model = CLIPModel.from_pretrained("openai/clip-vit-base-patch32")
processor = CLIPProcessor.from_pretrained("openai/clip-vit-base-patch32")

labels = ["a photo of a cat", "a photo of a dog", "a photo of a bird"]
inputs = processor(text=labels, images=image, return_tensors="pt", padding=True)
outputs = model(**inputs)
probs = outputs.logits_per_image.softmax(dim=1)
```

Zero-shot CLIP gets ~75% on ImageNet (vs. 85% for a fine-tuned CNN). For your specific dataset, lift varies.

Use cases:

- Brand new dataset, want immediate baseline.
- Labels change frequently.
- Broad / visually distinct categories.
- Image search (use image-image similarity instead).

Limitations:

- Worse on fine-grained classes (bird species, medical findings).
- Sensitive to prompt templates ("a photo of a {class}" vs "{class}" matters).
- Slower than fine-tuned small models for high-volume.

## Evaluation: what to report

Beyond top-1 accuracy:

| Metric                                    | Use for                            |
| ----------------------------------------- | ---------------------------------- |
| Top-1, top-5 accuracy                     | Overall quality                    |
| Per-class precision/recall/F1             | Where errors are                   |
| Macro F1                                  | Balanced metric across classes     |
| Confusion matrix                          | Which classes confuse model        |
| Calibration (reliability plot)            | Are probabilities trustworthy?     |
| Slice metrics                             | Per-camera, per-location, per-time |
| ImageNet-C / robustness suite             | Distribution shift                 |
| Manual error inspection (50-100 examples) | Systematic failures                |

A production-quality model report includes all of the above. Top-1 alone is for benchmarks, not production decisions.

## Common failure modes

| Symptom                                  | Likely cause                                         | Fix                                                                                   |
| ---------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Train acc 95%, val acc 70%               | Overfitting                                          | Strong augmentation, regularisation, smaller model                                    |
| Both stuck at ~random                    | Underfit or pipeline bug                             | Single-batch overfit test; check labels                                               |
| Validation oscillates wildly             | Learning rate too high; small batches with BatchNorm | Lower lr; SyncBatchNorm; LayerNorm backbone                                           |
| Validation good, production bad          | Distribution shift                                   | Domain-specific augmentation; distillation from CLIP; add production data to training |
| Per-class accuracy: 99% common, 30% rare | Imbalance                                            | Weighted loss, class-balanced sampling, focal loss                                    |
| Top-1 high, calibration awful            | Common after fine-tuning                             | Temperature scaling on validation set                                                 |

Trace problems systematically. Diagnose before reflexively changing the model.

## Deployment: from notebook to production

A trained classifier in production:

1. **Export** to ONNX or TorchScript for portability.
2. **Quantise** to INT8 (with calibration) for 2-4× speedup; FP16 / BF16 as a softer option.
3. **Compile** with TensorRT (NVIDIA), OpenVINO (Intel), or CoreML (Apple) for max throughput.
4. **Batch** requests for higher GPU throughput.
5. **Monitor** prediction distribution and per-class accuracy on sampled production data.

A quantised ConvNeXt-Tiny serves ~1000 req/s on a single mid-range GPU with p99 latency under 50ms. Sufficient for most production needs.
