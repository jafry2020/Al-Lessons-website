  - question: "When should you use spot instances?"
    shortAnswer: |
      Training workloads that can checkpoint and resume; batch inference; non-real-time serving. Spot is 50-70% cheaper but can be reclaimed with seconds-to-minutes notice. Real-time serving with strict SLAs: avoid spot.
    detailed: |
      Spot pricing offers 50-70% discount on cloud GPUs but with the catch that the cloud can reclaim the instance with 30 sec - 2 min notice.

      Good fits:
      - **Training jobs that checkpoint frequently**. Save every 10-30 min; resume from last checkpoint on reclamation.
      - **Batch inference**: process backlog jobs; partial completion is fine.
      - **Hyperparameter sweeps**: each trial is independent; loss of one trial is acceptable.
      - **Background async work**: e.g., regenerating image embeddings for a corpus.

      Bad fits:
      - **Real-time user-facing serving** with SLA: reclamation breaks SLA.
      - **Long single-machine training without checkpointing**: full loss on reclamation.
      - **Distributed training with limited fault tolerance**: failure of one node crashes the run.

      Workflow patterns:
      - **Spot for training**, on-demand for serving.
      - **Spot pool for stateless batch workers**.
      - **Multi-cloud / multi-zone for higher availability**: less likely all clouds reclaim at once.

      Tools: SageMaker spot training, Ray with autoscaler, Kubernetes Karpenter with diversified instance types.

      Spot savings can take a $5k/month training bill to $1.5k/month. Worth the engineering for high-volume training.
    pitfalls:
      - "Some clouds offer 'preemptible' or 'spot' with different SLAs. Read the fine print on notice time and reclamation rate."
  - question: "What's distillation and when is it the right call?"
    shortAnswer: |
      Train a small "student" model on the outputs of a large "teacher" model. Student matches teacher quality on the specific task at 10-100× cheaper inference. Worth the up-front cost at high volume.
    detailed: |
      Pattern:

      1. Use a frontier model (GPT-4o, Claude, Llama-70B) to generate outputs on a large unlabelled corpus.
      2. Use those outputs as labels for training a small model (encoder for classification, smaller LLM for generation).
      3. Deploy the small model at production volume.

      Quality: student often retains 95-99% of teacher's quality on the specific task. Loses generality.

      Cost savings:
      - GPT-4o at $0.005/req × 1M req/day = $5k/day.
      - Fine-tuned encoder at $0.0001/req × 1M req/day = $100/day.
      - 50× cost reduction; one-time fine-tune cost ($100-500).

      Break-even: distillation makes sense at ~10k+ daily requests.

      Process:
      1. Collect labelled or pseudo-labelled data using the teacher (10k-1M examples typically).
      2. Train the small model.
      3. Evaluate against the teacher on a held-out set.
      4. Deploy if quality is acceptable.

      Variants:
      - **Hard distillation**: use teacher's argmax predictions as hard labels.
      - **Soft distillation**: use teacher's full probability distribution.
      - **Response distillation** (for generation): use teacher's text outputs as targets.

      Watch out: legal terms. Some API providers (OpenAI) restrict using their outputs to train competing models. Check terms before distilling commercial APIs.
    pitfalls:
      - "Distilled models lose general capability. They're great at the trained task; can't reason outside it. Don't expect open-ended performance."
  - question: "How do quantisation and batching reduce cost?"
    shortAnswer: |
      Quantisation (INT8, INT4) cuts memory and compute 2-4×, fitting larger models on smaller GPUs and serving more requests per GPU. Batching raises GPU utilisation from ~10% (single inference) to 60-80% (batched), dropping cost per request 3-10×.
    detailed: |
      **Quantisation**:
      - FP32 → INT8: 4× memory cut, 2-4× speedup (CV + small LLMs).
      - FP16 / BF16 → INT4 (LLMs via GPTQ, AWQ, bitsandbytes): another 2-4× memory cut, ~1.5× speedup.

      Quality impact: typically 0-2% drop with calibration / careful methods.

      Effect on cost:
      - Llama-70B FP16 needs 140 GB → A100 80GB × 2 or H100 × 1.
      - Llama-70B INT4 needs ~40 GB → fits on 1× A100 or even L40S (48GB).
      - Per-request cost can drop 4-10× from this alone.

      **Batching**:
      - GPU utilisation at batch 1: ~10%.
      - At batch 16: ~60%.
      - At batch 64+: 70-85%.
      - Per-request compute amortised across the batch.
      - Per-request cost drops 5-10× for the same workload.

      For LLM serving specifically: vLLM's continuous batching + PagedAttention + INT4 quantisation can reduce cost per token 10-20× vs. unoptimised serving.

      Implementation:
      - Self-hosted: use vLLM or TensorRT-LLM for LLMs; ONNX Runtime / TensorRT for CV models.
      - APIs: providers may automatically batch internally; you control quantisation only via model choice.
    pitfalls:
      - "Quantisation can degrade quality on tail cases. Always evaluate on production-like data, not just held-out test."

## GPU choice matters

Pick the smallest GPU that meets latency and batch size needs:

| GPU          | Memory    | When                                           |
| ------------ | --------- | ---------------------------------------------- |
| H100 / H200  | 80-141 GB | Frontier LLM training; 70B+ LLM serving        |
| A100 (80 GB) | 80 GB     | Mid-range LLMs; serious training               |
| L40S         | 48 GB     | Mid-LLMs; cheaper than A100 for many workloads |
| A10 / L4     | 24 GB     | Small LLMs (7B with quantisation); CV training |
| T4           | 16 GB     | Small CV models; cheap inference               |
| CPU          | —         | Tiny models; spike-y traffic; legacy           |

Cloud rates (approximate 2026, vary by provider / region):

| GPU       | On-demand $/hr | Spot $/hr |
| --------- | -------------- | --------- |
| H100      | $3-8           | $1-3      |
| A100 80GB | $1.5-3         | $0.5-1.5  |

Smaller GPU at higher utilisation often beats larger GPU at low utilisation.

## Spot instances: 50-70% cheaper

Spot GPUs cost half to a third of on-demand. Catch: cloud can reclaim with 30 sec - 2 min notice.

Use spot for:

- **Training jobs that checkpoint frequently** (save every 10-30 min; resume on reclamation).
- **Batch inference / async work** (partial completion fine).
- **Hyperparameter sweeps** (trials are independent).

Don't use spot for:

- **Real-time user-facing serving** with SLA.
- **Long single-machine training without checkpointing**.

Tools that help: SageMaker spot training, Ray autoscaler, Kubernetes with Karpenter and diversified instance types.

A $5k/month training bill can become $1.5k/month with spot. Worth the engineering for sustained training workloads.

## Quantisation: 2-4× speedup / 4× memory cut

Quantise model weights to lower precision:

| Precision   | Memory | Speedup           | Quality cost |
| ----------- | ------ | ----------------- | ------------ |
| FP32        | 1×     | 1×                | 0            |
| BF16 / FP16 | 0.5×   | 1.5-2×            | Negligible   |
| INT8        | 0.25×  | 2-4×              | 0-2%         |
| INT4 (LLMs) | 0.125× | 1.5× more vs INT8 | 0-3%         |

For LLMs in 2026: GPTQ, AWQ, bitsandbytes are standard INT4 implementations.

Cost effect:

- Llama-70B FP16: 140 GB → 2× A100 80GB or 1× H100.
- Llama-70B INT4: 40 GB → 1× A100 or L40S.
- Per-request cost can drop 4-10×.

For CV in 2026: ONNX Runtime / TensorRT with INT8 calibration; PyTorch quantisation tooling. See A7.8.

## Batching: 3-10× cost reduction

GPU at batch size 1: ~10% utilisation. At batch 32+: 60-80% utilisation. Same hardware; 3-10× the throughput.

For LLMs specifically: vLLM's continuous batching at the token level is the production standard. Costs per token drop 5-10× vs unbatched serving.

For CV / NLP encoders: BentoML, Triton handle dynamic batching. Configure max batch size and timeout for your latency target.

Don't over-batch for real-time UX: long batch waits hurt p99 latency. Tune for your specific latency SLO.

## Distillation: 100× cheaper at high volume

Pattern (covered in earlier modules):

1. Use frontier LLM (GPT-4o, Claude, Llama-70B) to generate outputs on a large pseudo-labelled corpus.
2. Train a small model (encoder, small LLM) on those outputs.
3. Deploy the small model.

Quality retained: typically 95-99% of teacher.

Cost saved: 50-1000×.

Break-even: ~10k daily requests. Below that, the up-front fine-tune cost doesn't amortise.

Watch out: licensing terms. Some API providers restrict training competing models on their outputs.

## Multi-tenancy

For teams with many models, share resources:

| Pattern                                                            | Savings                                                 |
| ------------------------------------------------------------------ | ------------------------------------------------------- |
| **Triton multi-model serving** on one GPU                          | Multiple small models share a GPU instead of 1 GPU each |
| **vLLM serving multiple LoRA adapters** on one base model          | Adapters share base model weights                       |
| **Model fleet routing**: many small models on few large GPUs       | Better utilisation than per-model GPUs                  |
| **Shared embedding model**: one embedder for many downstream tasks | One inference per input, many uses                      |

Multi-tenancy adds operational complexity (noisy-neighbour issues, fair scheduling) but cuts costs significantly at scale.

For LoRA-fine-tuned LLMs specifically: vLLM's multi-LoRA serves dozens of LoRA adapters on one base model — game-changing for cost.

## Cost optimisation checklist

When the bill is too high:

1. **Right-size GPUs**: smallest that meets latency / batch needs.
2. **Quantise** (INT8 / INT4): 2-4× memory + speed gain.
3. **Batch** (continuous batching for LLMs): 3-10× cost reduction.
4. **Spot for training**: 50-70% cheaper.
5. **Distill** frontier → fine-tuned: 50-1000× cheaper at high volume.
6. **Prompt caching** (for LLMs): 50-90% on stable prefixes.
7. **Model routing**: cheap model for simple cases, frontier for complex.
8. **Auto-scale** to demand: pay for idle = wasted spend.
9. **Negotiate cloud rates / commit discounts**: 20-50% off list price at sustained spend.
10. **Multi-tenancy**: share GPU resources across models.

Most teams that achieve sustainable economics apply 4-7 of these.

## Closing for cost

ML cost optimisation is engineering, not negotiation. The biggest gains come from architectural choices (right-sized GPUs, batching, quantisation, distillation) applied with care. Monitor cost per request as a first-class metric. Apply the optimisation levers in priority order: quantisation + batching + right-size GPU first; distillation when scale justifies.
