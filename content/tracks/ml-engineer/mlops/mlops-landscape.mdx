  - question: "What is MLOps, in one sentence?"
    shortAnswer: |
      The operational discipline of building and running ML systems in production: experiment tracking, data versioning, model packaging, serving, monitoring, drift detection, retraining. Distinct from but overlapping with DevOps and data engineering.
    detailed: |
      MLOps emerged because ML systems break in ways traditional software doesn't:

      - **The data changes.** Models trained on yesterday's data behave differently on today's. Software code doesn't have this problem.
      - **Behaviour drifts silently.** A bug in code throws an exception. A model that degrades gradually shows no errors — just worse predictions.
      - **Training is non-deterministic.** Same code, same data: different model (different seeds, hardware, library versions). Reproducibility requires explicit effort.
      - **The model is data + code + hyperparams.** Versioning all three matters.
      - **Training and serving environments differ.** Even when "the same code," subtle preprocessing differences cause silent quality regressions.

      So MLOps adds tooling for: data versioning, experiment tracking, model registries, automated evaluation, drift detection, A/B testing, retraining pipelines.

      It overlaps with DevOps (CI/CD, infrastructure, monitoring) and data engineering (pipelines, storage, quality), but the ML-specific concerns are real and need dedicated attention.
    pitfalls:
      - "MLOps tools are often sold as platforms. Most teams need 5 lightweight tools, not one heavy platform."
  - question: "What's the production ML lifecycle?"
    shortAnswer: |
      Data → experiment → train → evaluate → register → package → deploy → monitor → retrain. Each step has tooling. Maturity ladder: from 'manual scripts' to 'CI-driven retraining' to 'continuous deployment.'
    detailed: |
      The canonical loop:

      1. **Data ingestion + versioning**: collect labelled data; version it (DVC, LakeFS, or git-LFS).
      2. **Experimentation + tracking**: run experiments; track every config, metric, artefact (W&B, MLflow).
      3. **Training**: scaled or single-node training; reproducible.
      4. **Evaluation**: against held-out, golden set, robustness suite.
      5. **Model registry**: versioned models with metadata (training data version, metrics, lineage).
      6. **Packaging**: containerise or export to inference format (ONNX, TensorRT, CoreML).
      7. **Deployment**: serve via container, batch job, or edge runtime.
      8. **Monitoring**: latency, error rate, prediction distribution, drift.
      9. **Retraining trigger**: scheduled, drift-driven, or performance-driven.
      10. **A/B testing or shadow traffic**: validate new models against current production.

      MLOps maturity levels (Google's MLOps framework):
      - **Level 0**: scripts and notebooks. Manual deployment. Most teams start here.
      - **Level 1**: orchestrated training + monitoring. Pipelines exist.
      - **Level 2**: CI/CD for ML — automated retraining, A/B, rollback.

      Most production ML in 2026 lives between Level 0 and Level 1. Level 2 is enterprise / mature teams.
    pitfalls:
      - "Don't engineer for Level 2 maturity when you're at Level 0 traffic. Each step has cost; match to scale."

  - question: "How does MLOps differ from DevOps?"
    shortAnswer: |
      DevOps versions code; MLOps versions code + data + models. DevOps deploys binaries; MLOps deploys models that depend on data distributions. DevOps monitors for failures; MLOps monitors for accuracy drift. ML-specific concerns require ML-specific tools.
    detailed: |
      Side by side:

      | Concern | DevOps | MLOps |
      | ------- | ------ | ----- |
      | Versioning | Code | Code + data + model + hyperparams |
      | Reproducibility | Same code = same binary | Same code + data + seed + libs = (usually) same model |
      | Testing | Unit + integration tests | Plus: data validation, model evaluation, regression suites |
      | Monitoring | Latency, errors, uptime | Plus: prediction distribution, accuracy, drift |
      | Rollback | Git revert + redeploy binary | Git revert + revert model artefact + revert data version |
      | Failure modes | Exceptions, crashes | Plus: silent quality degradation, distribution shift |
      | Deployment | Stateless services | Stateful (model files, sometimes feature stores) |

      DevOps tools alone aren't enough for ML; you need additions for the data + model + drift dimensions.

      But also: MLOps without solid DevOps is fragile. Containerisation, CI, monitoring, infrastructure-as-code — all still required.
    pitfalls:
      - "Don't hire 'an MLOps engineer' to fix bad DevOps. The foundations matter."
  - question: "What's the single most impactful MLOps practice?"
    shortAnswer: |
      Tied: (a) experiment tracking with reproducible artefacts (you know what produced every model), and (b) a regression evaluation suite that runs on every change. Without either, production ML becomes guesswork.
    detailed: |
      Two practices give disproportionate value:

      **Experiment tracking + reproducibility.** Every model deployed should have: training data version, code commit, hyperparams, metrics, training environment. Without this, debugging a production regression is impossible.

      Tooling: W&B, MLflow, or even Git + structured logs. Minimum viable: log a JSON with the above for every training run.

      **Regression evaluation suite.** A curated set of (input, expected behaviour) cases that every model release must pass. Without this, prompt / data / code changes silently break things.

      - "Make the regression suite a release gate. If it fails, the deployment is blocked. Without enforcement, it stops being maintained."
  - question: "When do you need a 'unified ML platform' (Databricks, SageMaker, Vertex)?"
    shortAnswer: |
      Larger teams (20+ MLE), enterprise compliance requirements, integrated data lake + training + serving needs. For most teams, a curated set of best-of-breed tools beats a single platform on price and flexibility.
    detailed: |
      Unified ML platforms package: data lake, notebooks, training infra, model registry, serving, monitoring. Single vendor, single interface.

      Pros:
      - **Integration**: components designed to work together.
      - **Compliance**: SOC2, HIPAA, etc., often built in.
      - **Skills consolidation**: hire for one platform instead of five tools.
      - **Vendor management**: one contract, one support relationship.

      Cons:
      - **Cost**: 2-5× the bill of equivalent best-of-breed.

      When to choose:
      - Enterprise with compliance needs.
      - Team > 20 ML engineers.
      - Heavy ETL + training + serving integrated workflows.
      - Risk-averse leadership.

      - Startups, scale-ups (<20 ML team).
      - Open-source-friendly culture.
      - Specific workflows where the platform's defaults don't fit.

## Why MLOps is its own thing

Software systems break with exceptions, error logs, crashes. You see them.

ML systems break with silent quality degradation. The API returns 200 OK; the predictions are wrong.

Three properties make ML production different:

1. **Models depend on data distributions.** When traffic shifts (new users, new products, new regions), the model's quality changes without any code change.
2. **Training is non-deterministic.** Same code, same data: different model (different seeds, hardware, library versions). Without explicit reproducibility, you can't go back.
3. **The deployment artefact is data + code + hyperparams + metrics.** Versioning all four matters.

MLOps tooling addresses these specifically. Standard DevOps tooling does what it does well; MLOps adds layers for what's specific to ML.

## The production ML lifecycle

```
Data → Track experiments → Train → Evaluate → Register → Package → Deploy → Monitor → Retrain
                ↑                                                                       │
                └───────────────────────────────────────────────────────────────────────┘
```

Each step has dedicated tooling. The next seven lessons cover each in depth.

Three maturity levels (from Google's MLOps framework):

| Level | What it looks like                                                                                |
| ----- | ------------------------------------------------------------------------------------------------- |
| **0** | Manual scripts, notebooks, ad-hoc deployment. Most teams start here.                              |
| **1** | Orchestrated pipelines, automated monitoring, scheduled retraining.                               |
| **2** | CI/CD for ML — automated retraining triggered by data / quality, A/B testing, automated rollback. |

In 2026, **most production ML lives between Level 0 and Level 1**. Level 2 is enterprise mature. Don't over-engineer for higher maturity than your traffic justifies.

## The minimal 2026 stack

For a small team shipping ML to production:

| Concern                  | Tool (open / cheap)                              |
| ------------------------ | ------------------------------------------------ |
| Code versioning          | Git + GitHub                                     |
| Data versioning          | S3 / GCS + DVC or git-LFS                        |
| Experiment tracking      | Weights & Biases (free tier) or MLflow self-host |
| Training infra           | Modal, Lambda Labs, RunPod, vast.ai              |
| Model registry           | W&B / MLflow / HuggingFace Hub                   |
| Containers               | Docker                                           |
| Serving                  | BentoML, FastAPI, vLLM, Triton                   |
| Monitoring               | Datadog / Prometheus + Grafana                   |
| Drift detection          | Evidently AI (open source)                       |
| Orchestration            | GitHub Actions, Prefect, or simple cron          |
| Feature store (optional) | Feast (open) or skip                             |

Total monthly cost for a startup: ~$200-500. Scales with usage.

For larger teams (10+ MLE), add:

- **Triton** or **vLLM** for high-throughput inference.
- **Arize / WhyLabs / Fiddler** for ML-specific monitoring.
- **Feature store** if shared features become coordination overhead.
- **A/B testing infra** (in-house or LaunchDarkly).

For enterprises with compliance + integration needs: consider Databricks, SageMaker, or Vertex — but be honest about cost vs. flexibility.

## The two practices that matter most

If you do nothing else:

**1. Experiment tracking with reproducible artefacts.**

Every model you ship should have:

- Training data version (which dataset, which commit / hash).
- Code commit (git SHA).
- Hyperparameters (full config).
- Metrics (per-class, on held-out, on slices).
- Environment (Python version, library versions, hardware).

Without this, debugging a production regression is guesswork.

**2. A regression evaluation suite that runs on every change.**

A curated set of (input, expected behaviour) cases. Every model release must pass it. Without it, prompt changes, data changes, code changes silently break things.

For LLM-powered features: golden set + LLM-as-judge (see A6.8).

For traditional models: held-out test set with per-segment metrics.

These two together turn ML from "ship and pray" to "ship with confidence." The other MLOps practices are valuable but secondary.

## How ML differs from traditional software

A summary of the key differences:

| Aspect                | Software                | ML                                             |
| --------------------- | ----------------------- | ---------------------------------------------- |
| Versioning            | Code                    | Code + data + model + hyperparams              |
| Failure mode          | Exception               | Silent quality degradation                     |
| Testing               | Unit + integration      | Plus: data validation, model evaluation        |
| Reproducibility       | Same code = same binary | Same code + data + seed + libs (sometimes)     |
| Rollback              | Revert binary           | Revert model + data + code                     |
| Monitoring            | Latency, errors         | Plus: prediction distribution, accuracy, drift |
| Time to detect issues | Seconds (exceptions)    | Days-weeks (drift)                             |

These differences are why MLOps tooling exists. Most of the upcoming lessons address one specific difference.
