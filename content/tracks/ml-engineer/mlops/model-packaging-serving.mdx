  - question: "Containers: what to put in your Dockerfile?"
    shortAnswer: |
      Base from a slim Python or CUDA image, install dependencies in a layer, copy code, copy model (or download at startup), expose port, run the serving framework. Use multi-stage builds to keep production image small.
    detailed: |
      A typical 2026 Dockerfile for a CV model:

      ```dockerfile
      FROM nvidia/cuda:12.4.0-runtime-ubuntu22.04

      # System deps
      RUN apt-get update && apt-get install -y python3.11 python3-pip && rm -rf /var/lib/apt/lists/*

      WORKDIR /app

      # Install Python deps first (layer caching)
      COPY requirements.txt .
      RUN pip install --no-cache-dir -r requirements.txt

      # Copy code
      COPY src/ /app/src/

      # Either: copy model into image (faster cold start, larger image)
      COPY models/model.onnx /app/models/

      # Or: download at startup (smaller image, slower cold start)
      # ENV MODEL_URL=s3://...
      # ENTRYPOINT ["python", "-m", "src.serve"]

      EXPOSE 8000

      CMD ["python", "-m", "src.serve"]
      ```

      Multi-stage builds for smaller images:

      ```dockerfile
      FROM python:3.11 AS builder
      RUN pip install --target=/install onnxruntime-gpu

      FROM nvidia/cuda:12.4.0-runtime-ubuntu22.04
      COPY --from=builder /install /usr/lib/python3.11/site-packages
      ...
      ```

      Optimisations:
      - Pin versions in requirements.txt.
      - Use `.dockerignore` to exclude unneeded files.
      - Prefer slim base images (alpine isn't good for ML — use slim-debian or ubuntu).
      - For GPU: use NVIDIA's CUDA base images, matching the CUDA version of your deployment hardware.

      - "Don't bake in dev tools (Jupyter, debuggers) in the production image. Slimmer image, fewer security surface area."
  - question: "What does BentoML do?"
    shortAnswer: |
      ML-specific framework that handles model packaging (bento format), batching, versioning, and serving. Wraps FastAPI underneath with ML-aware enhancements. Easy ramp from notebook to production.
    detailed: |
      A BentoML service:

      ```python
      import bentoml
      from bentoml.io import JSON, Image, Text

      classifier = bentoml.pytorch.get("my_classifier:latest").to_runner()

      svc = bentoml.Service("my-classifier", runners=[classifier])

      @svc.api(input=Image(), output=JSON())
      async def predict(image):
          # Preprocess
          tensor = preprocess(image)
          # Inference (BentoML handles batching automatically)
          result = await classifier.async_run(tensor)
          # Postprocess
          return {"class": result.argmax().item(), "confidence": result.max().item()}
      ```

      Build a "bento" (versioned bundle):

      ```bash
      bentoml build  # creates a versioned bento
      bentoml containerize my-classifier:latest  # creates Docker image
      ```

      Deploy: `bentoml deploy` to BentoCloud, or push image to your registry and deploy via Kubernetes / Modal / etc.

      What BentoML adds vs raw FastAPI:
      - Automatic micro-batching of concurrent requests (improves GPU utilisation).
      - Model versioning + registry.
      - Inference adapters (PyTorch, TensorFlow, ONNX, etc.) with proper async handling.
      - One-command containerisation.
      - Built-in metrics endpoint.

      For most non-trivial ML serving: BentoML over FastAPI.
    pitfalls:
      - "BentoML's `pytorch.save_model` wraps the model; understand the artefact structure if you'll inspect outside BentoML."

  - question: "How do you handle batching for throughput?"
    shortAnswer: |
      Continuous (a.k.a. dynamic) batching: queue incoming requests; flush a batch when full or timeout. Triton, vLLM, BentoML all support this. For LLMs: vLLM's continuous batching with PagedAttention is the standard.
    detailed: |
      Single inference: GPU runs at ~10% utilisation. Batched inference: 60-80% utilisation. Throughput 3-10× higher.

      Static batching: client sends a batch of N. Wastes time waiting if requests trickle in.

      **Continuous (dynamic) batching**: serving framework holds incoming requests in a queue. Flushes the batch when either:
      - Batch size hits N (e.g., 32).
      - Timeout (e.g., 20 ms) elapses.

      Triton, BentoML, vLLM all implement this. For LLMs, vLLM's continuous batching is particularly important — it batches at the token level, not the request level (PagedAttention enables this).

      Configuration:
      - **Max batch size**: limited by GPU memory; tune via benchmarking.
      - **Timeout**: trade-off between throughput (longer wait = bigger batches) and tail latency (longer wait = worse p99).
      - **Preferred batch sizes**: Triton can prefer specific sizes (8, 16, 32) for optimal kernel selection.

      Production guidance:
      - Small models (CV classification): batch 32-128, timeout 10-20 ms.
      - Large LLMs (vLLM): continuous batching; tune `max_num_seqs`.
      - Real-time UX: smaller batches, shorter timeouts.
    pitfalls:
      - "Don't batch too aggressively for real-time UX. p99 latency suffers as batch wait time increases."
  - question: "What's the cold-start problem and how do you mitigate it?"
    shortAnswer: |
      First request to a new container takes seconds-to-minutes longer than subsequent (loading model, JIT compile, GPU warm-up). Mitigate by: preload at boot, keep-warm pools, model caching, smaller models, snapshot containers (Modal / Cloudflare).
    detailed: |
      Cold-start sources:
      - **Container start**: pulling image, starting process. 1-30s depending on image size.
      - **Library imports**: PyTorch, transformers can take 5-15s to import.
      - **Model loading**: large models from disk → GPU. 1-30s.
      - **JIT compilation**: first inference triggers PyTorch / TensorRT graph compilation. 1-10s.
      - **GPU warm-up**: first compute often slower than steady state.

      Mitigations:
      - **Preload at boot**: load model + warm up in the container's startup phase, not on first request.
      - **Health check** that returns only after warm-up complete.
      - **Keep-warm pools**: maintain N idle replicas; auto-scaling to zero adds cold-start cost.
      - **Smaller images** for faster container start.
      - **Model caching layer**: keep model files on local NVMe; faster than S3 fetch.
      - **Modal / Cloudflare Workers AI**: snapshot containers post-warm-up; restore from snapshot for near-instant cold start.

      For LLMs specifically: vLLM with prefix caching reduces effective cold start for shared system prompts.
    pitfalls:
      - "Auto-scale to zero saves money but adds cold-start latency. For latency-sensitive endpoints, keep at least one replica warm."

## The serving stack

A production-grade ML serving system has four layers:

```
Client (HTTP / gRPC)
        ↓
Load balancer / orchestrator (Kubernetes, Modal, etc.)
        ↓
Container (Docker)
        ↓
Serving framework (FastAPI, BentoML, Triton, vLLM)
        ↓
Model (PyTorch, ONNX, TensorRT)
```

Each layer has choices. Most decisions come down to: **how much ops capacity do you have, and how much traffic do you serve?**

## Container basics

Every serving deployment is a Docker container. A minimal Dockerfile:

```dockerfile
FROM nvidia/cuda:12.4.0-runtime-ubuntu22.04

RUN apt-get update && apt-get install -y python3.11 python3-pip \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY src/ /app/src/
COPY models/model.onnx /app/models/

EXPOSE 8000
CMD ["python", "-m", "src.serve"]
```

Optimisation principles:

- **Pin versions** in requirements.txt for reproducibility.
- **Slim base images** (debian-slim, distroless when possible).
- **Multi-stage builds** to keep production image small.
- **Layer caching**: install deps before copying source (deps change rarely; source changes often).
- **Use `.dockerignore`** to exclude tests, docs, dev configs.
- **Don't bake dev tools** (Jupyter, debuggers) into production images.

Image size matters: small images pull / start faster. CV models with PyTorch + CUDA: typically 3-6 GB. LLM serving with vLLM: 8-12 GB.

### BentoML

ML-aware wrapper that handles batching, versioning, and packaging:

```python
import bentoml
from bentoml.io import JSON, Image

classifier = bentoml.pytorch.get("my_classifier:latest").to_runner()
svc = bentoml.Service("my-classifier", runners=[classifier])

@svc.api(input=Image(), output=JSON())
async def predict(image):
    tensor = preprocess(image)
    result = await classifier.async_run(tensor)
    return {"class": result.argmax().item()}
```

Build a versioned bento: `bentoml build`. Containerise: `bentoml containerize`.

For most production CV / NLP serving: BentoML over plain FastAPI.

### vLLM for LLMs

The 2026 standard for LLM serving:

```bash
vllm serve meta-llama/Llama-3-8B-Instruct \
    --tensor-parallel-size 1 \
    --max-model-len 8192 \
    --gpu-memory-utilization 0.9
```

Exposes an OpenAI-compatible API. Continuous batching at token level, PagedAttention for memory efficiency, prefix caching for repeated prompts.

For self-hosted LLMs: vLLM is the default. TGI is the runner-up; SGLang for structured-output-heavy workloads.

### Triton for multi-model

When you have many models sharing GPU resources:

- Models registered in a model repository.
- Triton handles routing, batching, scheduling.
- Supports ONNX, TensorRT, PyTorch, custom Python backends.
- Built for production scale by NVIDIA.

Operational overhead higher than BentoML; payoff is throughput and multi-model density.

## Continuous batching

GPU compute is most efficient at high batch sizes. Continuous batching maximises utilisation:

```
Time:   t=0       t=10ms    t=20ms    t=30ms
Queue:  [req1]    [req1,    [batch    [empty]
                   req2,    of 4
                   req3,    flushed
                   req4]    → GPU]
```

The serving framework holds requests in a queue, flushes when batch full OR timeout hit.

Configuration:

- **Max batch size**: tune via benchmarking (memory limited).
- **Timeout**: trade-off — longer = bigger batches (throughput); shorter = lower p99 latency.

For LLMs, **vLLM's continuous batching is at the token level** (not request level). PagedAttention enables this — different requests at different stages of generation share a single GPU pass.

<AnalogyCallout>
  Continuous batching is like a bus that waits up to one minute or for ten people, whichever comes
  first. Without it, every passenger takes a taxi (one request per GPU pass) — wasteful. With it,
  you carry more passengers per trip without making anyone wait too long.
</AnalogyCallout>

## Cold starts: the silent UX killer

First request to a fresh container can take 5-60 seconds. Causes:

- **Container start**: 1-30s.
- **Python imports**: 5-15s.
- **Model loading**: 1-30s.
- **JIT compile**: 1-10s on first inference.
- **GPU warm-up**: ~1s.

Mitigations:

- **Preload at boot**: load model in container startup, not on first request.
- **Health check** returns 200 only after warm-up.
- **Keep-warm pools**: minimum N replicas always running.
- **Snapshot containers** (Modal, Cloudflare): restore from post-warm-up snapshot in ms.
- **Smaller models** (distillation, quantisation).
- **Local model cache** on NVMe SSD; faster than S3 fetch.

For real-time UX endpoints: never auto-scale to zero. The cold-start hit is worse than the savings.

For batch / async work: auto-scale to zero is fine; cold start is a non-issue.

## Health checks and graceful shutdown

Production-grade containers expose:

- **`/health`**: returns 200 when model loaded and ready. K8s / Modal use this for routing.
- **`/metrics`** (Prometheus format): exposes per-endpoint counts, latency histograms, GPU utilisation.
- **Graceful shutdown**: on SIGTERM, drain in-flight requests for N seconds before exiting.

Without these, your orchestrator can't route traffic correctly, monitor performance, or roll out updates safely.

```python
# FastAPI example
@app.get("/health")
async def health():
    if model is None or not model_ready:
        return JSONResponse(status_code=503, content={"status": "not ready"})
    return {"status": "healthy"}
```

## Auto-scaling signals

For ML workloads, naive CPU-based auto-scaling fails (GPU does the work; CPU stays low):

| Signal              | When useful                                 |
| ------------------- | ------------------------------------------- |
| CPU utilisation     | Rarely for GPU services                     |
| GPU utilisation     | Direct measure of saturation                |
| Queue depth         | Request rate exceeds capacity               |
| p99 latency         | Latency SLA violated                        |
| Concurrent requests | Coarse but reliable                         |
| Custom metrics      | Domain-specific (e.g., tokens/sec for LLMs) |

KServe and Modal support multi-signal auto-scaling. For Kubernetes: HPA with custom metrics from Prometheus.

## When to migrate from managed to self-hosted

Most teams start with Modal / Replicate. Migrate to Kubernetes when:

- **Cost crosses break-even**: typically ~$5k-10k/month on managed.
- **Latency SLAs tighten** beyond what serverless can deliver.
- **Need multi-model density** on shared GPUs (Triton excels here).
- **Compliance requires** your-VPC-only.
- **Ops team grows** to support it.

Migration is significant work (weeks to months). Don't do it pre-emptively.

## Closing for serving

Model serving in 2026 has a settled stack at each scale tier:

- **Prototyping / low volume**: BentoML on Modal / Replicate.
- **Production at moderate scale**: BentoML / Triton / vLLM on managed K8s (EKS, GKE).
- **Production at scale**: Triton / vLLM on self-managed K8s with KServe.

The serving framework matches the workload (vLLM for LLMs, Triton for multi-model). Continuous batching for throughput; preloading and keep-warm pools for cold-start latency. Health checks and graceful shutdown for production-grade behaviour.
