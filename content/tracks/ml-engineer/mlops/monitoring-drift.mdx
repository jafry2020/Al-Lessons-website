  - question: "What is data drift?"
    shortAnswer: |
      The distribution of inputs in production diverges from the distribution at training. The model still works (no exceptions) but its predictions are based on a world that's changed.
    detailed: |
      Types of drift:

      **Data drift (covariate shift)**: P(x) changes. Inputs look different than training. Example: a fraud model trained on pre-pandemic transactions; pandemic changed spending patterns.

      **Concept drift**: P(y|x) changes. Same inputs map to different correct outputs. Example: customer preferences shift; same demographic features now predict different products.

      **Label drift (prior shift)**: P(y) changes. Class proportions shift. Example: fraud rates rise from 1% to 3%.

      **Feature drift**: a specific feature's distribution changes (a column in a tabular model).

      Detecting drift:
      - **KS test, Wasserstein distance**: compare numerical distributions.
      - **PSI (Population Stability Index)**: standard in finance / risk modelling.
      - **Chi-squared**: categorical features.
      - **Embedding distance**: for high-dim or text / image; compare embedding statistics over time.
      - **Adversarial classifier**: train a classifier to distinguish training from production batches; if it succeeds, there's drift.

      Tools: Evidently AI, Arize, WhyLabs all implement these natively.

      Drift is not always bad. Sometimes it reflects real change you should adapt to (retrain). Sometimes it's a data pipeline bug (alert and fix).
    pitfalls:
      - "Don't treat any drift as failure. Set thresholds with expected variance in mind."
  - question: "How do you measure production accuracy without ground truth?"
    shortAnswer: |
      Sample production traffic for human review (slow but golden), use delayed-feedback signals (clicks, returns, refunds), use proxy metrics (confidence calibration, prediction distribution stability), and run shadow traffic against a known-good model.
    detailed: |
      Strategies when labels are delayed or unavailable:

      **Human review** of sampled predictions:
      - 50-500 random samples per week, reviewed by an internal team or labelling service.
      - Gold standard for accuracy but slow and expensive.

      **Delayed feedback signals**:
      - User actions (clicks, conversions, returns) as implicit labels.
      - Days-to-weeks delay; still earlier than ground truth.

      **Proxy metrics**:
      - Confidence calibration on production data (compare predicted prob to outcome where available).
      - Prediction distribution: are class proportions stable?
      - Embedding distance to training samples.

      **Shadow traffic**:
      - Send a copy of production traffic to a known-good (or known-baseline) model.
      - Compare predictions; large divergences indicate one or the other is drifting.

      **A/B tests** with explicit outcome tracking.

      For most production: combine 2-3 of these. Weekly human review for 100 samples + daily proxy metrics + monthly accuracy report when ground truth catches up.
    pitfalls:
      - "Delayed feedback is biased — selection bias of which predictions get user action. Account for it."

    detailed: |
      Alert design:

      **Page-worthy** (wake someone up at 3 AM):
      - Service down (50% error rate, > 1 minute).
      - p99 latency > 2× SLO for > 5 min.
      - Critical metric (e.g., fraud detection's catch rate) drops > 20% in an hour.

      **Slack channel** (resolve next business day):
      - Drift score above threshold.
      - Accuracy on sampled data below historical norm.
      - Cost per request rising > 30%.

      **Weekly digest**:
      - Trends in drift, accuracy, latency.
      - Cost summary.
      - Model performance per slice.

      **Don't alert**:
      - Tiny drift (within noise).
      - Single sample being wrong.
      - Slow-moving trends (monitor in dashboards, not alerts).

      Tools: PagerDuty for paging; Slack / email for non-urgent. Alert rules in Datadog / Prometheus AlertManager / Arize / WhyLabs.

      Tune iteratively. Every false page reduces signal value. Every missed alert reduces trust. Find the equilibrium for your system.
    pitfalls:
      - "If an alert fires more than once a week, it's probably noise. Tune the threshold or remove the alert."
  - question: "When does drift mean 'retrain'?"
    shortAnswer: |
      When drift correlates with accuracy regression on sampled production data. Drift alone isn't a retraining signal; some drift is fine. Accuracy decline + drift = retrain. Accuracy stable + drift = update monitoring baseline.
    detailed: |
      Drift is a signal, not a verdict. Two outcomes:

      **Real shift in the world**:
      - New product launches change feature distributions.
      - Seasonal patterns.
      - Demographic shifts in user base.
      - **Response**: retrain on recent data. Update training baseline.

      **Data pipeline bug**:
      - Feature computation changed.
      - New default value for missing data.
      - Sampling logic changed upstream.
      - **Response**: fix the bug. Don't retrain on bad data.

      **Expected fluctuation**:
      - Day-of-week / time-of-day variation.
      - Normal weekly cycles.
      - **Response**: no action; update threshold to account for variance.

      Decision rule: drift alone → investigate. Drift + accuracy regression → retrain or fix bug. Drift alone, accuracy stable → noise or expected variance.

      Build a retraining playbook: drift detected → check accuracy → if regressed, run retraining pipeline → evaluate against regression suite → deploy if better.
    pitfalls:
      - "Retraining is expensive. Don't trigger it on every drift signal; require concurrent accuracy regression."

## What to monitor

Two layers:

**Operational** (any service):

- Latency: p50, p95, p99.
- Throughput: requests/sec.
- Error rate: 4xx vs 5xx.
- Cost per request.
- Resource utilisation (CPU, GPU, memory).

**ML-specific** (what's different):

- Input feature distributions (histograms, top-k counts).
- Prediction distribution (class probabilities, confidence histograms).
- Drift scores (statistical distance from training distribution).
- Accuracy on sampled production data (when labels available).
- Per-class precision / recall over time.
- Per-segment metrics (user type, region, time-of-day).

The operational layer catches obvious failures. The ML-specific layer catches the silent quality regressions that uptime monitoring misses.

## Why ML monitoring is different

A traditional web service fails noisily — 500 errors, exception logs, dropped connections. You see it.

An ML service fails silently — same 200 OK responses, same latency, predictions just gradually become worse as the data distribution shifts. Users notice before you do, if you don't have ML-specific monitoring.

This is the operational difference covered in A8.1: silent quality degradation requires dedicated tooling.

## Detecting drift

Several statistical approaches:

| Method                               | Use for                                                     |
| ------------------------------------ | ----------------------------------------------------------- |
| **KS test**                          | Numerical features; compare CDFs                            |
| **Wasserstein distance**             | Numerical features; geometric distance                      |
| **PSI (Population Stability Index)** | Standard in finance; bins numerical or categorical          |
| **Chi-squared**                      | Categorical features                                        |
| **Embedding distance**               | High-dim, text, image                                       |
| **Adversarial classifier**           | Train classifier to distinguish train vs production batches |

Modern libraries (Evidently, Arize, WhyLabs) compute these for you. You provide a reference (training) distribution and a current (production) distribution; the library produces drift scores per feature plus overall.

For embeddings (text or image): cosine similarity between centroids of training embeddings and recent production embeddings. Distance growing = drift.

## A sample monitoring schema

For a tabular classifier:

```python
# Per-request, log:
{
    "timestamp": "2026-06-15T10:30:00Z",
    "request_id": "abc123",
    "input_features": {  # sampled or hashed for high-cardinality
        "age": 34,
        "income": 75000,
        "region": "EU",
        ...
    },
    "prediction": {
        "class": "approved",
        "probability": 0.87,
    },
    "model_version": "v2.4.1",
    "latency_ms": 23,
}

# Periodic batch jobs:
# - Aggregate to histograms (hourly).
# - Compute drift score (daily) vs training reference.
# - Sample 100 predictions/day for human review.
# - Roll up to per-segment accuracy when ground truth catches up.
```

Storage: write to a log aggregator (BigQuery, Snowflake, S3 + Athena). Aggregate in batch. Don't slow the inference path.

## Production accuracy without ground truth

Most production ML doesn't get instant ground truth. Strategies:

**Human review sample**:

- 50-500 predictions/week reviewed by internal team or labelling service.
- Slow and expensive but gold standard.

**Delayed feedback signals**:

- User actions (click, purchase, return, refund) as implicit labels.
- Days-to-weeks delay; still earlier than full ground truth.
- Biased by selection (which predictions actually trigger user action).

**Proxy metrics**:

- Confidence calibration: predicted prob vs observed rate where comparable.
- Prediction distribution stability: are class proportions drifting?
- Embedding distance: production samples diverging from training distribution.

**Shadow traffic**:

- Send a copy of requests to a known-good (or known-baseline) model.
- Compare predictions; large divergences suggest one is drifting.

**A/B tests** with explicit outcome tracking.

For most production: combine 2-3 of these. Weekly human review + daily proxy + monthly accuracy report when ground truth catches up.

## Alert tiering

Avoid alert fatigue:

| Tier                          | Examples                                                                                   | Channel           |
| ----------------------------- | ------------------------------------------------------------------------------------------ | ----------------- |
| **Page** (3 AM wake-up)       | 50% error rate > 1 min; p99 latency 2× SLO > 5 min; critical accuracy drop > 20% in 1 hour | PagerDuty         |
| **Slack** (next business day) | Drift score above threshold; accuracy regression on sample; cost rising > 30%              | Slack channel     |
| **Weekly digest**             | Trend reports across drift, accuracy, cost, latency                                        | Email / dashboard |
| **Don't alert**               | Single mispredictions; slow-moving drift within noise                                      | Just log          |

**If an alert fires more than weekly, it's probably noise.** Tune the threshold or remove the alert. Trust in monitoring depends on signal-to-noise.

## When does drift mean retrain?

Decision rule:

| Situation                      | Action                                                       |
| ------------------------------ | ------------------------------------------------------------ |
| Drift alone, accuracy stable   | Investigate; update monitoring baseline; no retrain          |
| Drift + accuracy regression    | Retrain on recent data                                       |
| Drift due to data pipeline bug | Fix the bug; don't retrain on bad data                       |
| No drift, accuracy stable      | All good                                                     |
| No drift, accuracy regression  | Suspicious — likely a deployment / serving bug, not training |

Drift detection should trigger investigation, not automatic retraining. Automatic retraining on every drift signal:

- Wastes compute.
- Risks training on bad / biased recent data.
- Can amplify a problem if the drift is a bug.

A reasonable retraining cadence: scheduled monthly + on-demand when drift correlates with accuracy regression.

## The cost of monitoring

Monitoring isn't free:

- **Storage**: logs of input features, predictions, and metadata can become TB / month.
- **Compute**: drift calculations are batch jobs.
- **Engineering**: maintenance, alert tuning, dashboard updates.

Cost-effective practices:

- **Sample, don't log everything**: 1-10% of requests for detailed feature logging.
- **Aggregate at ingestion**: histograms / counts instead of raw values.
- **Hash high-cardinality features**: log hash distributions, not values.
- **Tiered storage**: hot (last 30 days) on fast store; cold (older) on S3 Glacier.
- **Drift detection runs hourly / daily**, not per-request.

For a 100k requests/day service: monitoring infrastructure usually adds $50-200/month. Worth it.

## Closing for monitoring

ML monitoring is the discipline that turns 'we shipped a model' into 'we run a model in production reliably'. Both operational and ML-specific layers required. Drift detection is a signal, not a verdict — investigate before reacting. Alert tiering preserves signal value.
