      - GPT-4V on every ticket: ~$0.05-0.10 per ticket = $500-1000/day = $15k-30k/month. Hits cost budget.

## The framing

A SaaS company processes 10k support tickets per day. Currently triaged by humans (~2 min each = 200 hours of agent time daily). Goal: automate triage, surface high-priority, suggest drafts for routine inquiries.

Constraints:

- <30 seconds latency per ticket (already submitted; not real-time UX).
- <$0.05 per ticket cost.
- Agent reviews all outputs — ML is decision support, not autonomous.
- Privacy: PII redaction before sending text to external APIs.

## Metrics

- **Category**: macro F1 across 8 categories; per-class F1.
- **Priority**: recall on 'high' (missing one is bad); accuracy on low/medium.
- **Draft acceptance**: % drafts accepted by agent with minimal edits.
- **Image understanding**: per-task F1.
- **Operational**: time-to-triage, cost per ticket, tickets resolved per agent.
- **Business KPI**: CSAT, high-priority response time.

## Data

50k-500k historical tickets with text + images + agent labels + responses + outcomes.

Data quality concerns:

- Agent label noise (different agents pick different categories).
- Subjective priority (use outcomes like CSAT as secondary signal).
- PII redaction required before training.
- Image quality varies (screenshots clean; photos blurry).

## Pipeline architecture

```
Ticket arrives (text + maybe image)
        ↓
Preprocessing (PII redaction; image encoding; tokenisation)
        ↓
Stage 1: Category classification (fine-tuned ModernBERT)
        ↓
Stage 2: Priority classification (encoder + customer features)
        ↓
Stage 3 (if image): VLM image analysis (Claude vision)
        ↓
Stage 4: Draft response (RAG + GPT-4o-mini)
        ↓
Route to team queue
```

Why decomposed:

- Cheaper models on easier sub-tasks.
- Each stage independently evaluable and replaceable.
- Per-stage observability.
- Cost ~$0.01/ticket vs. $0.05-0.10 for monolithic GPT-4V.

<AnalogyCallout>
  A monolithic VLM is like asking a single senior consultant to do every task. A decomposed pipeline
  is a team — junior specialists for routine work, senior for hard cases. Total cost lower; quality
  often higher because each specialist is sharper at their narrow task.
</AnalogyCallout>

## Per-stage details

### Stage 1: Category classification

- **Model**: fine-tuned ModernBERT-base on 50-500k historical tickets.
- **Input**: ticket text (after PII redaction).
- **Output**: category (8 classes) + confidence.
- **Latency**: ~30ms on Triton.
- **Cost**: ~$0.0001 per ticket.
- **Quality**: macro F1 ~0.85 (limited by agent label inconsistency).

### Stage 2: Priority classification

- **Model**: same encoder backbone + customer metadata (account tier, recent activity, ticket length, sentiment).
- **Input**: ticket text + customer features.
- **Output**: priority (low / medium / high) + confidence.
- **Cost-weighted**: missing a 'high' is worse than over-classifying.
- **Latency**: ~30ms.

### Stage 3: Image analysis (when image present)

- **Model**: Claude 3.5 Sonnet vision (or LLaVA self-hosted at higher volume).
- **Prompt**: "Describe what's shown in this support ticket image. Identify if it's a screenshot of an error, a photo of hardware, a product photo. Extract any visible error text."
- **Output**: structured JSON with type + extracted text.
- **Latency**: ~2-5 seconds.
- **Cost**: ~$0.005-0.015 per image.

### Stage 4: Draft response

- **Retrieval**: embed ticket text with sentence-transformer; retrieve top-5 similar resolved tickets from pgvector.
- **Generation**: GPT-4o-mini with prompt:

```
You are a customer support agent. Draft a response to this ticket.

Use the resolution patterns from these similar past tickets as guidance:
[Top 5 retrieved tickets with their resolutions]

Current ticket:
[Text + image description if present]

Draft your response. Keep it under 200 words. Match the company's professional, helpful tone. If unsure, leave a note for the agent.
```

- **Output**: draft text + confidence (low confidence → agent edits more).
- **Latency**: ~3-8 seconds.
- **Cost**: ~$0.005 per draft.

## Evaluation strategy

**Per-stage CI**:

- Category: F1 on held-out test; 200-case regression suite.
- Priority: F1 on 'high'; cost-weighted accuracy.
- Image: F1 on labelled subset; manual sample.
- Draft: LLM-as-judge with rubric (helpfulness, accuracy, professionalism); human-validated correlation > 0.7.

**End-to-end golden set**: 200 curated tickets with expert categorisation, priority, ideal draft. Run full pipeline; compare per-stage.

**Production sampling**: 1% of tickets reviewed weekly by senior agents. Failures tagged by mode (wrong category, wrong priority, bad draft, image misread).

**Agent feedback loop**: track draft acceptance / edits / dismissal. High dismissal per category → retrain that area.

## Cost breakdown

Per-ticket cost:

| Stage                                 | Cost                   |
| ------------------------------------- | ---------------------- |
| Category encoder                      | ~$0.0001               |
| Priority encoder + features           | ~$0.0001               |
| Image (when present, ~40% of tickets) | ~$0.005 (amortised)    |
| RAG retrieval                         | ~$0.0005               |
| Draft generation (GPT-4o-mini)        | ~$0.005                |
| **Total average**                     | **~$0.011 per ticket** |

At 10k/day: ~$110/day = ~$3,300/month. Well under budget.

Compare to monolithic GPT-4V on every ticket: ~$0.05-0.10/ticket × 10k = $500-1,000/day = $15-30k/month. The decomposed pipeline saves $12k-27k/month.

## Operations

**Serving stack**:

- Triton for category + priority encoders (shared single GPU).
- Anthropic / OpenAI APIs for VLM and LLM.
- pgvector for RAG.
- BentoML orchestrates the multi-stage pipeline.

**Monitoring**:

- Per-stage latency p50/p99.
- Per-stage error rate.
- End-to-end success.
- Cost per ticket.
- Per-category prediction distribution drift.
- Draft acceptance rate (rolling weekly).

**Alerts**:

- Page: end-to-end success < 95% for 10 min.
- Slack: cost per ticket up 30%; draft acceptance trending down.
- Weekly digest: per-stage health, per-category metrics.

**Retraining**:

- Category: quarterly (or on accuracy drop).
- Priority: monthly (drift-sensitive).
- Drafts: no model retraining; updating RAG corpus + prompt template updates behaviour.

**Graceful degradation**:

- If RAG fails: skip drafts; still triage.
- If VLM fails: skip image analysis; flag image manually-reviewed.
- If category encoder fails: route to general queue for human triage.

System keeps working with degraded quality rather than failing entirely.

## Risks and mitigations

| Risk                                          | Mitigation                                                  |
| --------------------------------------------- | ----------------------------------------------------------- |
| LLM hallucinated draft                        | Agent always reviews; flag low-confidence drafts            |
| PII leakage to API                            | Redaction layer; audit logs; on-prem fallback for sensitive |
| Embedding drift (RAG quality decay)           | Re-embed quarterly; monitor retrieval relevance             |
| Cost spike on API                             | Per-ticket cost alerts; routing rules cap usage             |
| Vendor outage (OpenAI / Anthropic down)       | Fallback chain to other provider; circuit breakers          |
| Agent dissatisfaction (bad drafts annoy)      | Track satisfaction; iterate prompts based on edit patterns  |
| Bias (priority correlates with customer tier) | Per-segment audit quarterly                                 |

## Iteration plan

- **v0** (week 0-6): ship category classifier + simple priority rules. No drafts yet. Demonstrate triage value.
- **v1** (week 6-12): add fine-tuned priority + RAG + GPT-4o-mini drafts. Measure draft acceptance.
- **v2** (week 12-20): add VLM for images on >30% of tickets. Per-customer-tier routing logic.
- **v3** (week 20-32): per-category prompt tuning; specialised models for high-volume categories.
- **Ongoing**: quarterly retraining; monthly review of failure modes; cost optimisation.

## What this walkthrough shows

A multimodal ML system using the 7-step framework:

1. **Problem framing**: triage decision support; 10k/day; agent reviews all outputs.
2. **Metrics**: per-task (category F1, priority F1, draft acceptance) + operational + business.
3. **Data**: historical tickets + agent labels + outcomes; PII redaction.
4. **Modelling**: decomposed pipeline (encoder + encoder + VLM + RAG+LLM); cheaper than monolithic.
5. **Evaluation**: per-stage CI + golden set + production sample + agent feedback loop.
6. **Serving**: Triton + APIs + pgvector + BentoML; graceful degradation.
7. **Risk**: hallucination, PII leakage, drift, vendor outage — each with mitigation.

The framework applied to a problem dramatically different from fraud detection. Same structure; different choices at each step.
