importantQuestions:
  - question: "How does a tree choose where to split?"
    shortAnswer: "Greedily — at each node, try every feature and every threshold, pick the one that most reduces impurity (Gini or entropy for classification, variance for regression). No backtracking."
    detailed: |
      For a candidate split that divides n examples into left (n_L) and right (n_R) groups: impurity gain = parent_impurity − (n_L/n)·left_impurity − (n_R/n)·right_impurity. Gini impurity is 1 − Σ pₖ² where pₖ is class proportion. Entropy is −Σ pₖ log pₖ. They behave similarly; Gini is slightly cheaper to compute.

      The greedy choice is locally optimal but globally suboptimal — the best two-split structure isn't always built from the single best first split. CART (the standard algorithm, Breiman 1984) accepts this trade-off because considering all tree structures is NP-hard.
    pitfalls:
      - "Continuous features: the split candidates are between consecutive sorted unique values. For large n this is O(n log n) per feature per node."
  - question: "Why does a deep tree overfit?"
    shortAnswer: "It memorises. With enough depth, leaves contain one example each, training error is zero, and the tree captures noise as 'rules'. Generalisation is terrible."
    detailed: |
      A tree with no depth limit and no min-samples constraint will keep splitting until each leaf is pure. On training data, accuracy is 100%. On any new data, predictions follow the noise pattern in training, not the signal. This is the textbook example of low bias, sky-high variance.

      Controls (hyperparameters every tree library exposes): max_depth, min_samples_split, min_samples_leaf, max_leaf_nodes. In practice, depth 4–10 with min_samples_leaf around 1% of training size is a reasonable starting point. The honest answer for "what depth?" is "tune on a validation set."
    pitfalls:
      - "Cost-complexity pruning (post-fit) is rarely used today — most practitioners constrain depth up-front and ensemble for variance reduction."
  - question: "Why are trees rarely deployed as single models?"
    shortAnswer: "Variance. A single tree's structure changes wildly with small data perturbations, so its predictions are unstable. Ensembles (random forests, gradient boosting) average this away."
    detailed: |
      Trees have very high variance: take 80% of your training data, fit a tree; do it again on a different 80%, and you'll often get a completely different tree. Predictions vary too. The bias-variance argument says: average many trees and the variance shrinks while bias stays the same.

      Random forests do this with bagging (next lesson). Gradient boosting goes further, fitting each tree to correct the previous ensemble's mistakes — and dominates tabular ML in 2026 in the forms of XGBoost, LightGBM, and CatBoost. The single tree is a building block, not a final answer.
    pitfalls:
      - "Decision trees are still used as final models when interpretability is legally required (credit decisions, healthcare). One tree you can explain beats an ensemble you can't."
  - question: "When do trees beat linear models?"
    shortAnswer: "When the relationship between features and target is non-linear, when feature interactions matter, or when features are on different scales and types. Linear models need careful engineering for the same behaviour."
    detailed: |
      Trees handle three things natively that linear models don't: non-linearity (any monotonic transformation of a feature gives the same tree), interactions (deep trees represent x₁ × x₂ patterns without engineering), and mixed feature types (categoricals + numerics + missingness, with the right library).

      They lose to linear models when: the data is high-dimensional and sparse (text features, embeddings — millions of dimensions with few non-zero entries each), the relationships actually are linear, or you need extreme interpretability and fast inference. NLP and computer vision moved to deep models partly because trees don't scale to those dimensions.
    pitfalls:
      - "Trees can't extrapolate. Predictions outside the training feature range are clipped to the training extremes."
  - question: "What's the difference between Gini and entropy?"
    shortAnswer: "Tiny. Both measure impurity; they agree on most splits. Entropy slightly prefers more balanced splits; Gini is cheaper to compute. In practice the choice rarely changes anything."
    detailed: |
      Gini = 1 − Σ pₖ². Entropy = −Σ pₖ log pₖ. Plot them as functions of p for binary classification: both are maximum at p=0.5 (most impure) and zero at p=0 or 1 (pure). The curves differ slightly in shape but the ordering of candidate splits is almost always the same.

      Trees are mostly tuned by structural hyperparameters (depth, samples-per-leaf, regularisation), not the impurity measure. Scikit-learn's default is Gini; libraries like LightGBM use specialised variants. Don't waste time on this knob.
    pitfalls:
      - "For regression trees: the impurity is variance (or MSE within a node). Same idea, different formula."
  - question: "How do trees handle categorical features?"
    shortAnswer: "Scikit-learn requires you to one-hot or label encode first — neither is ideal. LightGBM and CatBoost handle categoricals natively, considering all subset splits, which is dramatically better for high-cardinality features."
    detailed: |
      A categorical feature with K values has 2^(K−1) − 1 possible subset splits. Scanning them all is expensive but Fisher (1958) showed an O(K log K) trick when the target is binary or regression: sort categories by mean target, then split at thresholds in that ordering. LightGBM uses this.

      One-hot encoding works but explodes the feature count and forces the tree into single-category splits, losing the subset structure. Label encoding (assigning integers) implies an ordering that may not exist — the tree treats 'red' < 'blue' < 'green' as meaningful.

      In production for tabular work: pick a library with native categorical support and pass categorical features as-is.
    pitfalls:
      - "Target encoding (replacing a category with its target mean) leaks information; use proper out-of-fold encoding (see lesson A2.8)."

<TldrCallout>
  A decision tree partitions the feature space into rectangles by greedily splitting on the feature
  and threshold that most reduce impurity. Single trees overfit easily — depth and
  minimum-samples-per-leaf are the main controls — and modern tabular ML uses them only as building
  blocks of ensembles (random forests, gradient boosting).
</TldrCallout>

## The model

A tree is a sequence of if-else questions: "Is feature 3 > 0.4? If yes, ask about feature 7. If no, ask about feature 1." Each leaf holds a prediction (a class for classification, a number for regression). Inference is O(depth), which is fast.

Trees are **non-parametric**: the number of "parameters" (splits) is set by the data, not fixed in advance. This is why they can fit arbitrarily complex patterns — and why they overfit so easily.

## How a split is chosen

At every node, the algorithm tries every feature and every candidate threshold, and picks the split that most reduces impurity. For classification with Gini:

Gini(node) = 1 − Σₖ pₖ²

For a candidate split into left and right children:

Gain = Gini(parent) − [n_L/n · Gini(left) + n_R/n · Gini(right)]

Larger gain = better split. Repeat recursively in each child until a stopping criterion (max depth, min samples, no positive gain) is hit.

<AnalogyCallout>
  Imagine carving a chunk of marble into clean white and clean black pieces by making one straight
  cut at a time. Each cut should leave the two halves more uniformly coloured than before. The order
  and angle of cuts is greedy: pick the best cut now and never reconsider.
</AnalogyCallout>

Things to notice:

- The optimal first split (highest gain) is usually obvious visually — it's where one half is mostly one class.
- A "balanced" split (50/50 samples) isn't always optimal — what matters is class purity per side.
- For real datasets in many dimensions, you can't eyeball the best feature. The algorithm scans them all.

## Why one tree is not enough

Train a tree, hold 20% of data out, score it. Now retrain on a different 80%. The resulting tree often looks structurally different — different root, different splits — and predictions on borderline points flip. This is **high variance**: predictions are unstable across resamplings of training data.

Two ways forward, both covered in the next lessons:

- **Bagging** (random forests). Fit many trees on bootstrap samples, average their predictions. Variance shrinks as O(1/B) where B is the number of trees.
- **Boosting** (XGBoost, LightGBM). Fit each tree to correct the previous ensemble's mistakes. Reduces both bias and variance. This is what wins tabular ML in 2026.

A single tree is a building block. As a final model, deploy it only when interpretability or auditing forces it.

## Trees in 2026: where they fit in the stack

| Use case                                | Use a single tree?     | Better choice                  |
| --------------------------------------- | ---------------------- | ------------------------------ |
| Regulated credit / healthcare decisions | Yes (interpretability) | Often required by law          |
| Tabular Kaggle / business problem       | No                     | XGBoost / LightGBM / CatBoost  |
| Feature importance for analysis         | Sometimes              | Permutation importance on RF   |
| Real-time inference at scale            | Yes if very shallow    | Compiled tree (Treelite, ONNX) |
| Text or image data                      | No                     | Transformers / CNNs            |

The honest summary: a single tree is taught because it makes the ensembling story make sense, not because you'll often deploy one. The next four lessons (A2.4 random forests, A2.5 gradient boosting, A2.6 SVMs, A2.7 kNN) are about what people actually ship.

## A note on libraries

`sklearn.tree.DecisionTreeClassifier` is the canonical implementation: CART, Gini default, single-threaded, no native categorical support. Useful for learning, rarely used in production. The libraries that matter — XGBoost, LightGBM, CatBoost — are built on the tree primitive but with serious engineering on top (next two lessons).
